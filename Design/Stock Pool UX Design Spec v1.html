Stock Pool UX Design Spec v1

โปรเจกต์ Store management system saas · วันที่ 2026-08-03 · ยังไม่ใช่ implementation

1. เป้าหมายและ Success Criteria

  • ผู้ใช้เพิ่มสินค้าเข้า stock flow ได้จากหน้า Stock โดยไม่ต้องสลับไปหน้าเมนูสินค้า
  • หากสินค้าไม่มี Variant ระบบเปิด Dialog สร้าง Variant และไม่อนุญาตให้ไปต่อจนสร้างสำเร็จ
  • Variant จากสินค้าคนละรายการแชร์ Stock Pool เดียวกันได้
  • ผู้ใช้แยกความหมาย “รับเข้า” กับ “กำหนดยอดใหม่” ได้จากข้อความและตัวอย่างบนหน้าจอ
  • POS/QR ตัดและคืนยอดจาก Pool แบบ atomic โดยไม่ติดลบและไม่ตัดซ้ำ

2. คำศัพท์ที่ใช้ใน UI

สินค้า

รายการที่ลูกค้าเห็น เช่น “เบียร์สิงห์” หรือ “โปรเบียร์สิงห์ 3 ขวด”

Variant — รูปแบบที่ขาย

รูปแบบขายของสินค้า เช่น 1 ขวด, 3 ขวด, S/M/L แต่ละ Variant กำหนดราคาเพิ่ม/ลดและจำนวนหน่วยจาก Stock Pool ที่ใช้ต่อการขายหนึ่งรายการ

Stock Pool — สต๊อกกลาง

ยอดของจริงในคลัง มีชื่อ หน่วยนับ ยอดคงเหลือ และเกณฑ์แจ้งเตือน Variant หลายตัวจากหลายสินค้าใช้ร่วมกันได้

จำนวนที่ตัดต่อการขาย

ตัวคูณการใช้ Pool เช่น Variant “3 ขวด” ใช้ 3 หน่วยเมื่อขายหนึ่งรายการ

3. User Flow

เลือกสินค้าค้นจากเมนูสินค้า
เลือก Variantหรือสร้างใน Dialog
เลือก Poolสร้างใหม่/ใช้ร่วม
กำหนดการใช้เช่น 1 หรือ 3 หน่วย
ปรับยอดรับเข้า/กำหนดใหม่

กรณีไม่มี Variant

  1. แสดงคำอธิบายว่า Variant คือ “รูปแบบที่ขายจริง” และเสนอชื่อเริ่มต้น ปกติ
  2. บังคับกรอกชื่อ Variant; ราคาเพิ่ม/ลดเริ่มต้นเป็น 0
  3. สร้างสำเร็จแล้วเลือก Variant ใหม่นั้นให้อัตโนมัติและคง Dialog เดิมไว้

4. วิธีปรับยอด

โหมดความหมายตัวอย่างข้อกำหนด
รับเข้าบวกจำนวนเข้ากับยอดเดิม30 + 12 = 42จำนวนต้องมากกว่า 0; ระบุหมายเหตุได้

6. Runtime/Data Flow

ขายสินค้า

  1. รวมยอดการใช้ตาม Pool: จำนวนขาย × consumption_quantity
  2. ล็อก Pool ตามลำดับ id ด้วย FOR UPDATE เพื่อหลีกเลี่ยง deadlock
  3. ตรวจยอดทุก Pool ก่อนหัก หากรายการใดไม่พอให้ rollback ทั้ง transaction
  4. หักยอดและบันทึก movement ใน transaction เดียวกับ order/payment

ยกเลิก/void

คืนยอดตาม link และ consumption ที่ snapshot ไว้กับ order item ตอนขาย เพื่อไม่ให้การแก้ link ภายหลังเปลี่ยนจำนวนที่ต้องคืน

ปรับยอดด้วยมือ

RPC ทำ atomic update และสร้าง movement; server action ตรวจ stock.manage, package entitlement และ store boundary ซ้ำทุกครั้ง

7. Migration Strategy

  1. สร้างตารางใหม่และ RLS โดยไม่ลบ field เดิม
  2. Variant ที่ track_stock=true แต่ละตัวได้รับ dedicated Pool ยอดเท่ากับ stock_quantity และ consumption = 1
  3. เปลี่ยน POS/QR/Stock page มาอ่าน Pool หลัง backfill verification ผ่าน
  4. คง field เดิมในช่วง compatibility window; การลบ field เดิมเป็น migration ภายหลังและต้องอนุมัติแยก

8. Error Handling

  • Variant ถูกผูกกับ Pool อื่นแล้ว: แสดง Pool ปัจจุบันและต้องยืนยันการย้าย โดยห้ามย้ายระหว่าง checkout ที่กำลังทำงาน
  • Pool คนละร้าน: ปฏิเสธที่ DB/RLS และ server boundary
  • สต๊อกไม่พอ: แสดง Pool, ยอดคงเหลือ และยอดที่ต้องใช้
  • กรอกจำนวนว่าง: ไม่แปลงเป็น 0; แสดง validation error
  • การสร้าง Variant/Pool ล้มเหลว: Dialog คงข้อมูลเดิมและให้ลองใหม่ ไม่เปลี่ยนหน้า

9. Testing

  • Unit/UI: คำอธิบาย Variant, Dialog บังคับสร้าง Variant, receive/set-balance validation, package gate
  • Repository/RPC: หลาย Variant ใช้ Pool เดียว, multiplier, insufficient stock, atomic rollback
  • POS/QR: ไม่ตัดซ้ำ, cancel/item void คืนตาม snapshot, concurrent checkout ไม่ติดลบ
  • Migration: backfill quantity เท่าของเดิมทุก Variant และ tenant/store isolation
  • Manual responsive QA: desktop/mobile, keyboard focus, dialog nested state และข้อความผิดพลาด

10. Out of Scope v1

  • หนึ่ง Variant ตัดหลาย Pool หรือสูตรวัตถุดิบ/BOM
  • แชร์ Pool ข้ามสาขา, โอนสต๊อก และ purchase order
  • สต๊อกทศนิยม/น้ำหนัก
  • การลบ field stock เดิมทันที

Deployment gate: ต้อง dry-run/backfill verify, backup, code review และอนุมัติ production migration แยกก่อน deploy
