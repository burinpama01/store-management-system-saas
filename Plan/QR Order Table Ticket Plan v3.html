บิลรวมโต๊ะ + จองสต็อกจนครัวรับออเดอร์

แผน v3 · 2026-09-18 · ต่อจาก v2 + ความต้องการใหม่เรื่องสต็อก · สถานะ: รออนุมัติ · ใช้กับ POS ปกติ /pos + บอร์ด QR เดิม (ไม่แตะ Unified POS)

1. ความต้องการใหม่ (เพิ่มจาก v2)

ลูกค้ากดสั่งผ่าน QR → สต็อกที่แสดงบนหน้าจอลูกค้าลดลงทันที (จองไว้) → ออเดอร์เด้งเข้าครัว → ครัวกด "รับออเดอร์" จึงตัดสต็อกจริง → ถ้าครัว ปฏิเสธ คืนสต็อก

ข้อเท็จจริงตอนนี้: ระบบ ตัดสต็อกจริงทันทีที่ลูกค้าสั่ง · บอร์ดครัวไม่มีปุ่มรับออเดอร์ (มีแค่ "เริ่มเตรียม") · ปฏิเสธรายละรายการได้แล้ว (คืนสต็อก) · หน้าลูกค้ายังไม่แสดงสต็อกเลย

2. โมเดลสต็อกใหม่: "จอง" แยกจาก "ตัดจริง"

สต็อกจริง (หลังร้าน/รายงาน)      = stock_quantity                  ← ลดตอนครัวรับเท่านั้น
ยอดจอง                            = reserved_quantity               ← เพิ่มตอนลูกค้าสั่ง
พร้อมขาย (หน้าลูกค้า/POS/เช็คของ) = stock_quantity − reserved_quantity
เหตุการณ์stock_quantityreserved_quantitystock_movements
ลูกค้ากดสั่ง—+ จำนวน (ถ้าพร้อมขายไม่พอ = สั่งไม่ได้)reserve
ครัวกด รับออเดอร์− จำนวน− จำนวนsale (ตัดจริง)
ครัว ปฏิเสธ (ทั้งออเดอร์หรือรายรายการ)—− จำนวนrelease
ปฏิเสธรายการที่ รับไปแล้ว+ จำนวน (คืนเหมือนเดิม)—return
ปิดโต๊ะ/ยกเลิกออเดอร์ที่ยังไม่รับ—− จำนวนrelease

ทำเหมือนกันกับ Stock Pool (stock_pools.reserved_units) เพราะออเดอร์ QR ใช้ pool ได้ · ทุกจุดที่เช็ค "ของพอไหม" (POS, QR, เดลิเวอรี, AI) เปลี่ยนไปใช้ยอด พร้อมขาย

ครัวรับออเดอร์

  • บอร์ด QR: ออเดอร์สถานะ "ใหม่" มีปุ่ม รับออเดอร์ (แทน "เริ่มเตรียม") และ ปฏิเสธ
  • ร้านที่มีหลายสถานีครัว: แต่ละสถานีกดรับเฉพาะรายการของสถานีตัวเอง (ตัดสต็อกเฉพาะรายการนั้น) — ออเดอร์ขยับเป็น "กำลังเตรียม" เมื่อทุกสถานีรับแล้ว
  • รายการจากตั๋วหน้าร้าน (POS) ไม่ผ่านการจอง — ตัดสต็อกตอนรวมบิล/ชำระตามเดิม

หน้าจอลูกค้า

  • เมนูที่ติดตามสต็อก: แสดง "หมด" เมื่อพร้อมขาย ≤ 0 · (ตัวเลือก) แสดง "เหลือ n" เมื่อใกล้หมด
  • ตรวจซ้ำฝั่ง DB ตอนสั่งเสมอ (ล็อกแถว) — กันลูกค้าสองโต๊ะแย่งชิ้นสุดท้าย

3. บิลรวมโต๊ะ (จาก v2 คงเดิม)

  1. เปิดโต๊ะ → เปิดตั๋วโต๊ะแบบ atomic (1 ตั๋วอัตโนมัติต่อโต๊ะ)
  2. ออเดอร์ QR โผล่ในตั๋ว พร้อมสถานะ รอครัวรับ / รับแล้ว / ปฏิเสธ
  3. พิมพ์ใบตรวจรายการ (ยังไม่ชำระ) ให้ลูกค้าเช็ค · แก้ก่อนจ่ายได้
  4. กดชำระ → server รวมทุกออเดอร์ของโต๊ะเป็น บิลเดียว → หน้าจ่ายเงินปกติของ POS (เงินสด/Beam/TrueMoney ตามนโยบายเดียวกัน) → ใบเสร็จใบเดียว → ปิดโต๊ะ
  5. ใหม่: ถ้ายังมีรายการที่ครัว ยังไม่รับ → ห้ามรวมบิล แจ้ง "รอครัวรับ/ปฏิเสธก่อน" (ไม่เก็บเงินของที่ยังไม่ยืนยันว่ามี)

บิลรวมตั้ง qr_order_source = true (จ่ายแล้วไม่ตัดซ้ำ) · รายการ QR ถูกตัดจริงแล้วตอนครัวรับ · รายการตั๋วหน้าร้านตัดตอนรวมบิล

4. แก้ตามรีวิว PR #62 (คงจาก v2)

  • ชำระผ่านหน้าจ่ายเงิน POS → นโยบาย Beam/พร้อมเพย์เดียวกัน · Beam ยัง 1 การจ่าย : 1 ออเดอร์
  • ตั๋วโต๊ะจ่ายแล้วปิดโต๊ะเสมอ (มีหรือไม่มี QR)
  • ticket_source + unique index + RPC ensure_table_auto_ticket · query ตั๋วตามโต๊ะไม่ติด limit 30
  • safe logging + audit การลบตั๋วว่าง · test พฤติกรรม + SQL integration

5. Migration (additive)

  • product_variants.reserved_quantity, stock_pools.reserved_units (default 0, check ≥ 0)
  • order_items.stock_state: reserved | committed | released (+ รายการเก่า = committed)
  • แก้ RPC: create_qr_order_with_items (จองแทนตัด), void_qr_order_item, cancel_qr_order (คืนตามสถานะ) · ใหม่: accept_qr_order_items
  • จาก v2: pos_saved_tickets.ticket_source, orders.merged_into_order_id, ensure_table_auto_ticket, consolidate_table_bill, stores.table_open_auto_ticket

6. ความเสี่ยง

  • ออเดอร์ที่เปิดค้างอยู่ตอน deploy ตัดสต็อกไปแล้ว → migration ตั้ง stock_state = committed ทั้งหมด (ไม่จองซ้ำ ไม่คืนผิด)
  • ถ้าครัวไม่กดรับเลย สต็อกค้างจอง → แสดงยอดจองค้างในหน้าสต็อก + ปล่อยคืนอัตโนมัติเมื่อปิดโต๊ะ/ยกเลิก
  • ทุกจุดที่เช็คสต็อก (POS ปกติ, ขายส่ง, เดลิเวอรี, Stock Pool, Unified) ต้องเปลี่ยนไปใช้ "พร้อมขาย" — ถ้าหลุดจุดเดียว = ขายเกิน · จะมี test ครอบทุกจุด
  • ร้าน Unified POS (นำร่อง) มีระบบครัว/รับ-ปฏิเสธของตัวเอง — รอบนี้ ไม่เปลี่ยนจังหวะตัดสต็อกของ Unified (แต่ให้เช็คยอดพร้อมขายด้วย)
  • ระบบเงิน + สต็อก + DB เดียวกับ prod → ทดสอบบน Supabase local (Docker) ก่อน apply
  • ขนาดงาน: ประมาณ 3–4 วันทำงาน → แนะนำแบ่ง 2 PR
