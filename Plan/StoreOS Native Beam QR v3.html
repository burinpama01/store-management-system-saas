POS รอบถัดไป: Beam QR

สถานะ: เสนอขอบเขตเพื่อยืนยันก่อนแก้ payment flow · เครื่องพิมพ์พักไว้

แนวทาง

แนะนำทำ native QR โดยเชื่อมบริการ Beam เดิมของเว็บ เพื่อคงการตรวจยอด สิทธิ์ และสถานะบน server ทางเลือกเปิดเว็บชำระทำได้เร็วกว่าแต่สลับหน้าจอ; ทำ gateway ใหม่จะเพิ่มกติกาซ้ำและความเสี่ยง จึงไม่เลือกสองทางนี้

กลับไปยังรายการเดิม

ขอบเขต implementation

  1. ตรวจ quote จาก server ก่อนสร้างคำขอ เก็บ operation ID และ gateway payment ID เดิมสำหรับ retry ไม่สร้างใหม่เมื่อผลไม่ทราบ
  2. เพิ่ม scoped native API สำหรับความพร้อม สร้าง QR และอ่านสถานะ โดยเรียก createBeamQrPayment / refreshBeamPayment เดิม ใช้ bearer และ permission/feature ตามเว็บ
  3. เชื่อม native checkout กับ gateway ที่ยืนยัน PAID พร้อมตรวจยอด ร้าน และป้องกันใช้ charge เดียวซ้ำ ต้องตรวจ transaction/claim ของเว็บก่อนเลือก RPC ไม่เดาว่า schema เดิมพอ
  4. แสดง QR, loading/error/expired และคืน pending payment หลังเปิดแอปใหม่ ห้ามแสดงสำเร็จจากรูป QR หรือการกดปุ่มเอง
  5. ระหว่าง pending ล็อก cart/customer/discount/coupon; เมื่อเน็ตหลุดให้ค้นรายการเดิม ไม่สลับเงินสดหรือสร้าง charge ใหม่เงียบ ๆ
  6. เพิ่ม tests สำหรับข้ามร้าน/ยอดผิด/chargeซ้ำ/PAID/timeout/restore แล้ว reviewer ตรวจก่อน build

การตรวจและขอบเขต production

เริ่มด้วย mock provider และ test fixture ในเครื่อง ไม่สร้าง charge จริง ไม่รับเงินจริง ไม่ deploy prod หรือ migration ใหม่จนเห็น diff และผ่าน reviewer พร้อมขออนุมัติผลรอบนั้น

หากพบต้องแก้ schema ให้เสนอ additive migration พร้อม backup/restore/dry-run ก่อนลง production

Version bump ก่อน build/commit; คงธีมเดิม ปุ่มอย่างน้อย48px และตรวจ iPhone/iPad/keyboard

เกณฑ์ผ่าน

ชำระเฉพาะยอด server; retries คืนรายการเดิม; ยืนยันจาก provider และ gateway ที่ผูกกับร้าน; charge ไม่ถูกใช้ซ้ำ; ปิดเปิดแอปยังคืน pending ได้; ไม่อ้าง prod/device ผ่านจาก mock tests
