1. วิสัยทัศน์ & โมเดล

เชื่อม StoreOS (ระบบหลัง/POS ของร้าน) เข้ากับ JDC (แอปเดลิเวอรี/ลูกค้า/คนขับ) ผ่านตัวกลาง StoreOS Connect โดยจำลองโมเดลจริงของ LINE MAN × Wongnai POS

ในโลกจริง Wongnai POS คือระบบ POS ในร้าน ส่วน LINE MAN คือ marketplace + คนขับ ทั้งสองเป็นคนละบริษัท คนละฐานข้อมูล สื่อสารกันผ่าน Partner API + Webhook โดยมีหลักการสำคัญ 4 ข้อ:

  • POS เป็นแหล่งความจริงของเมนู — ร้านจัดการเมนู/ราคา/สต็อกที่เดียว แล้วดันขึ้น marketplace
  • ออเดอร์จาก marketplace ไหลเข้า POS อัตโนมัติ — ไม่ต้องคีย์ซ้ำ ลดข้อผิดพลาด
  • สถานะวิ่งกลับ marketplace แบบ real-time — รับ/กำลังทำ/พร้อมรับ → จ่ายงานคนขับ
  • เปิด-ปิดร้าน & ของหมด sync สองทาง — ลูกค้าเห็นสถานะตรงกับหน้าร้านจริง
ข้อค้นพบสำคัญที่กำหนดสถาปัตยกรรม: StoreOS (lcsxee…supabase.co) กับ JDC (tfwhf…supabase.co) อยู่ คนละ Supabase project → StoreOS Connect ต้องเป็น API/Event bridge ระหว่าง 2 ฐานข้อมูล ไม่ใช่ query ข้ามตารางในฐานเดียว — ซึ่งตรงกับโมเดล LINE MAN × Wongnai พอดี

5. รูปแบบการเชื่อม — ทำไมเลือก "Contract API" ไม่ใช่ "Direct DB"

ตัวเลือก A — Direct DB ไม่เลือก

StoreOS ถือ service-role key ของ JDC แล้ว read/write ตาราง JDC ตรง ๆ

  • ✗ StoreOS เก็บกุญแจหลักของ JDC = เสี่ยงสูง
  • ✗ ข้าม business logic ของ JDC (RPC create_food_order, RLS, การจ่ายงานคนขับ)
  • ✗ ผูกติด schema ภายในของ JDC แตกง่ายเวลา JDC แก้ตาราง

ตัวเลือก B — Contract API + Webhook เลือก

นิยาม "สัญญา" กลาง: JDC เปิด Edge Functions ไม่กี่ตัวเป็น Partner API, StoreOS Connect เรียกผ่านสัญญานี้ และ JDC ยิง webhook ออเดอร์กลับ

  • ✓ decoupled — แต่ละฝั่งแก้ภายในได้อิสระตราบใดที่สัญญาเดิม
  • ✓ เคารพ business logic เดิมของ JDC (RPC/RLS/จ่ายงานคนขับ)
  • ✓ ขยายไป channel จริง (LINE MAN/Grab) ในอนาคตได้ด้วย adapter เดียวกัน
เนื่องจากคุณเป็นเจ้าของทั้งสองระบบ งานฝั่ง JDC จึงเบามาก — แค่ Edge Functions 3 ตัว + 1 DB trigger ส่ง webhook ออก ส่วน "สมอง" ของ integration อยู่ในโมดูล Connect ใน StoreOS ตามที่เลือก

6. ตารางข้อมูลใหม่ (ฝั่ง StoreOS / Supabase A)

ทุกตารางมี organization_id + RLS org-scoped เหมือนตารางอื่นของ StoreOS

-- 1) การผูกร้าน StoreOS ↔ ช่องทางขายภายนอก (MVP: ผูกด้วยมือ)
create table connect_channel_links (
  id                 uuid primary key default uuid_generate_v4(),
  organization_id    uuid not null references organizations(id) on delete cascade,
  store_id           uuid not null references stores(id) on delete cascade,
  channel            text not null default 'jdc',          -- เผื่ออนาคต: lineman/grab
  external_merchant_id text not null,                      -- profiles.id ฝั่ง JDC
  status             text not null default 'active',        -- active|paused|disconnected
  webhook_secret     text not null,                         -- HMAC แชร์ต่อ link (เก็บ hash/encrypted)
  commission_rate    numeric(5,2) not null default 0,       -- % ค่า GP (เผื่อ settlement Phase 2)
  auto_accept        boolean not null default false,        -- รับออเดอร์อัตโนมัติหรือรอกดรับ
  config             jsonb not null default '{}',
  created_at         timestamptz not null default now(),
  updated_at         timestamptz not null default now(),
  unique (store_id, channel)
);

-- 2) แผนที่สินค้า StoreOS ↔ เมนูปลายทาง
create table connect_menu_map (
  id                 uuid primary key default uuid_generate_v4(),
  link_id            uuid not null references connect_channel_links(id) on delete cascade,
  product_id         uuid not null references products(id) on delete cascade,
  external_item_id   text,                                  -- menu_items.id ฝั่ง JDC (เติมหลัง sync ครั้งแรก)
  sync_hash          text,                                  -- hash ของ field ที่ดันไป กันดันซ้ำ
  last_synced_at     timestamptz,
  last_error         text,
  unique (link_id, product_id)
);

-- 3) ออเดอร์ที่รับเข้ามาจากช่องทางภายนอก (idempotency + reconciliation)
create table connect_orders (
  id                 uuid primary key default uuid_generate_v4(),
  organization_id    uuid not null references organizations(id) on delete cascade,
  link_id            uuid not null references connect_channel_links(id) on delete cascade,
  external_order_id  text not null,                         -- bookings.id ฝั่ง JDC
  internal_order_id  uuid references orders(id) on delete set null,
  channel            text not null default 'jdc',
  fulfillment_status text not null default 'received',      -- received|accepted|preparing|ready|completed|cancelled
  raw_payload        jsonb not null,
  received_at        timestamptz not null default now(),
  unique (link_id, external_order_id)                       -- กันรับซ้ำ
);

-- 4) คิว event สองทาง (outbox/inbox) + retry + audit
create table connect_events (
  id            uuid primary key default uuid_generate_v4(),
  link_id       uuid not null references connect_channel_links(id) on delete cascade,
  direction     text not null,                               -- outbound|inbound
  topic         text not null,                               -- menu.upsert|order.created|order.status|shop.status
  payload       jsonb not null,
  status        text not null default 'pending',             -- pending|sent|failed|dead
  attempts      int not null default 0,
  next_retry_at timestamptz,
  last_error    text,
  created_at    timestamptz not null default now()
);
ช่องว่างที่ต้องเติมในออเดอร์ StoreOS: ตาราง orders เดิมมี status = draft/open/pending_payment/paid/… ซึ่ง ไม่มีสถานะครัวแบบ accepted/preparing/ready สำหรับเดลิเวอรี → ใช้ connect_orders.fulfillment_status เป็นตัวเก็บสถานะ fulfillment ของช่องทาง + ผูกกับ kitchen ticket เดิม (จาก feature auto-print/station routing) แทนการแก้ enum หลักของ orders

F1. Sync เมนู / ราคา / สต็อก StoreOS → JDC

1
ร้านสร้าง/แก้สินค้าใน StoreOS หรือกดปุ่ม "เผยแพร่ขึ้น JDC" → DB trigger เขียน event ลง connect_events (outbound, topic menu.upsert)
2
Connect worker (cron/หลังเขียน) อ่าน event → map field ตาม §7.1 → เทียบ sync_hash ถ้าไม่เปลี่ยนข้าม
3
เรียก JDC Edge Fn connect_upsert_menu (เซ็น HMAC) → JDC upsert ลง menu_items ของ merchant ที่ผูกไว้
4
บันทึก external_item_id + last_synced_at ลง connect_menu_map; ของหมด/ปิดขาย → ส่ง is_available=false
มี cron reconcile รายชั่วโมงเทียบ map vs ปลายทาง กันกรณี event หลุด + ปุ่ม "Sync ทั้งหมดตอนนี้" สำหรับ initial load

F2. รับออเดอร์เข้า POS JDC → StoreOS

1
ลูกค้าสั่งอาหารใน JDC → สร้าง booking (food) + ชำระเงินออนไลน์
2
DB trigger ฝั่ง JDC ยิง webhook order.created มาที่ POST /api/connect/v1/webhooks/jdc/order (เซ็น HMAC + timestamp)
3
Connect ตรวจ signature → เช็ค idempotency ด้วย booking.id (unique) → map รายการผ่าน connect_menu_map
4
สร้าง orders + order_items ในร้าน (source = jdc) + insert connect_orders (fulfillment received)
5
ออเดอร์โผล่บน POS/KDS + พิมพ์ตั๋วครัวอัตโนมัติ (ต่อยอด feature auto-print เดิม) → ถ้า auto_accept ข้ามไป F3 ทันที
กันออเดอร์หาย: webhook ต้องตอบ 2xx เร็ว (รับเข้า inbox ก่อน ประมวลผล async) + JDC retry ถ้าไม่ 2xx + idempotency กันซ้ำ

F3. Sync สถานะออเดอร์ StoreOS → JDC

1
พนักงานกด รับออเดอร์ / กำลังทำ / พร้อมรับ บนหน้า POS หรือ KDS
2
อัปเดต connect_orders.fulfillment_status → enqueue event order.status
3
map สถานะตาม §7.3 → เรียก JDC Edge Fn connect_update_order_status
4
JDC อัปเดต booking → จ่ายงานคนขับ (matched/ready_for_pickup) → แจ้งลูกค้า (FCM)

F4. เปิด-ปิดร้าน & ของหมด สองทาง

1
ร้านเปิด/ปิดรับออเดอร์เดลิเวอรีใน StoreOS → event shop.status → JDC Edge Fn set_shop_status เซ็ต profiles.shop_status
2
สินค้าหมด/ปิดขายใน StoreOS → ส่ง menu.upsert (is_available=false) ตาม F1
ฝั่งกลับ (optional MVP+): ถ้า JDC ปิดร้านเอง/ของหมดฝั่ง JDC → webhook กลับมาแจ้ง StoreOS เพื่อแสดงสถานะตรงกัน

8. API Contract (สัญญากลาง)

ขาเข้า StoreOS Connect (JDC เรียก)

POST /api/connect/v1/webhooks/jdc/order        # ออเดอร์ใหม่ / ยกเลิกจากลูกค้า
Headers: X-Connect-Signature: sha256=...  X-Connect-Timestamp: ...
Body: { booking_id, merchant_id, items:[{menu_item_id,qty,price,name}],
        customer:{...}, dropoff:{...}, total, paid:true }
→ 202 { received:true, connect_order_id }

ขาออก StoreOS Connect (เรียก JDC Edge Functions)

POST {JDC}/functions/v1/connect_upsert_menu
Body: { merchant_id, items:[{external_ref, name, description, price,
        image_url, is_available, category, preparation_time}] }

POST {JDC}/functions/v1/connect_update_order_status
Body: { booking_id, status }                   # map แล้วตาม §7.3

POST {JDC}/functions/v1/connect_set_shop_status
Body: { merchant_id, is_open }

ของเดิมที่ใช้ต่อ (StoreOS public API)

GET /api/v1/products|orders|inventory|customers + api_keys auth + Enterprise gate — ใช้สำหรับ pull/รายงาน/ตรวจสอบ

9. Security & Reliability

ความปลอดภัย

  • HMAC signature สองทาง — secret ต่อ link (webhook_secret) + timestamp กัน replay (≤5 นาที)
  • ไม่เก็บ service key ของ JDC แบบ plaintext ใน DB — เก็บใน Vercel env / secret store, อ้างอิงด้วย ref
  • ต่อยอด api_keys เดิม + scope ใหม่ connect + billing gate Enterprise
  • RLS org-scoped ทุกตาราง connect_*

ความทนทาน

  • Outbox/Inbox + retry แบบ backoff (connect_events) → dead-letter เมื่อเกินจำนวนครั้ง
  • Idempotency — order ใช้ booking_id unique, menu ใช้ sync_hash
  • Reconcile cron รายชั่วโมง เทียบ map/สถานะ กัน event หลุด
  • หน้า admin ดู event ที่ fail + กด retry ด้วยมือ
ตาม AGENTS.md: ห้ามฝัง/เปิดเผย API key — ทุก secret ของ JDC ต้องตั้งใน Vercel env ของ StoreOS เป็น blocker ที่ต้องขอจากผู้ใช้ก่อน deploy (ยังไม่ใส่ในแผนนี้)

11. Roadmap & Phase

Phase 0 — ฐานราก (เริ่มก่อน)
  • migration: ตาราง connect_* 4 ตัว + RLS
  • โมดูล src/modules/connect/ (repository, mapping, JDC client, hmac util)
  • หน้า admin "ผูกร้านด้วยมือ" (store_id ↔ merchant_id) + สร้าง webhook secret
  • นิยาม API contract + สเปก JDC Edge Functions (ส่งให้ฝั่ง JDC)
Phase 1a — Menu/Price/Stock sync (F1 + F4 ของหมด)
  • menu sync service + sync_hash + ปุ่ม Sync now + JDC Edge Fn connect_upsert_menu
Phase 1b — รับออเดอร์เข้า POS (F2)
  • webhook in + idempotency + map → สร้าง order + แสดงบน POS/KDS + ตั๋วครัว
Phase 1c — Sync สถานะ + เปิด-ปิดร้าน (F3 + F4)
  • status push + ปุ่มสถานะบน POS + JDC Edge Fn update_status/set_shop_status
Phase 2 — ความน่าเชื่อถือ + ธุรกิจ
  • reconcile cron, dashboard event fail/retry, settlement/ค่า GP, รายงานยอดเดลิเวอรี, auto-provision linking
Phase 3 — Multi-channel abstraction
  • ยกชั้น channel adapter ให้รองรับ LINE MAN/GrabFood จริงในอนาคตด้วยโครงเดียวกัน

การชำระเงิน & settlementJDC เก็บเงินลูกค้าออนไลน์ → StoreOS mark order เป็นจ่ายแล้วยังไง? ค่า GP/payout คิดที่ไหน?กระทบบัญชี/cashflow — แนะนำลงรายละเอียด Phase 2 แต่ต้องตัดสินใจ mark-as-paid ตั้งแต่ F2
Modifiers / ตัวเลือกเมนูStoreOS มี product_variants + modifiers (jsonb) ส่วน JDC มี menu_options — โครงต่างกันMVP อาจ sync เฉพาะสินค้าหลัก + ราคา ยังไม่ map modifier เต็ม
หมวดหมู่StoreOS category = FK, JDC = text → ส่งชื่อหมวด; ถ้าชื่อซ้ำ/เปลี่ยนต้องจัดการต่ำ
สถานะครัวในเดลิเวอรีorders.status เดิมไม่มี accepted/preparing/ready → ใช้ connect_orders.fulfillment_status + kitchen ticketออกแบบไว้แล้ว แต่ต้องเชื่อมกับ KDS เดิม
Secrets ฝั่ง JDCต้องตั้ง JDC service key + webhook secret ใน Vercel env ของ StoreOSBlocker — ต้องขอจากผู้ใช้ก่อน deploy
หลาย store ต่อ orgorg เดียวมีหลายสาขา → link ต่อ store, mapping ต่อ storeออกแบบ schema รองรับแล้ว (unique store_id+channel)
