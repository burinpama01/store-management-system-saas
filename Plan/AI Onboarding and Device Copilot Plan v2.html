1. สิ่งที่ตรวจพบจากโค้ดจริง (ต้องอ่านก่อนตัดสินใจ)

1.1 ⚠️ iPad / iPhone ไม่มีแอป — และนั่นตัดทางเลือกอุปกรณ์ทิ้งไปหมด

mobile/README.md ระบุชัด: “Build iOS ทำบนเครื่องนี้ไม่ได้ (Windows) — ใช้ Codemagic build → TestFlight (Phase 4)” และในโค้ดมีแค่ route /download/android ไม่มีของ iOS

ผลที่ตามมา: iPad ใช้ Safari → ไม่มี Web Bluetooth, ไม่มี WebUSB, และไม่มีแอปให้ใช้ native BLE → เหลือทางพิมพ์ทางเดียวคือ Print Hub หรือเครื่องพิมพ์ IP
แปลว่า Print Hub คือเส้นเลือดใหญ่ของผู้ใช้ iPad ทั้งหมด ไม่ใช่ทางเลือกเสริม

  • .storeos-app เป็น grid 256px + 1fr และมี override เป็น flex ที่ max-width:767px เท่านั้น

อ้างอิงจาก bluetooth-client.ts, usb-client.ts, native-print-client.ts, network-print-client.ts — นี่คือข้อมูลที่ detectCapabilities() ต้องคืนให้ถูก

นี่คือเหตุผลว่าทำไม “ตัดตัวเลือกที่ใช้ไม่ได้ทิ้ง” ถึงสำคัญกว่า AI: ตารางนี้เป็นความจริงตายตัว เขียนเป็น if/else ได้ทั้งหมด และมันแก้ปัญหาผู้ใช้ iPad ที่กดปุ่มบลูทูธแล้วเจอ error วนไปเรื่อย ๆ ได้ทันทีโดยไม่ต้องเรียกโมเดลสักครั้ง

3. ใครใช้อุปกรณ์อะไร (persona × device)

บทบาทอุปกรณ์หลักทำอะไรจริง ๆต้องการจากหน้าจอ
เจ้าของ / ผู้จัดการมือถือ (นอกร้าน) + Windows (ในออฟฟิศ)ดูยอด อนุมัติ ตอบแจ้งเตือน / ทำรายงาน เงินเดือน ตั้งค่ามือถือ = อ่านอย่างเดียว เร็ว ๆ · Windows = ตารางใหญ่ ฟอร์มยาว
แคชเชียร์Windows ประจำเคาน์เตอร์ หรือแท็บเล็ตขายอย่างเดียว ทั้งวัน ต่อเนื่องปุ่มใหญ่ ไม่ต้องเลื่อน ตะกร้าเห็นตลอด
พนักงานเสิร์ฟมือถือลงเวลา รับออเดอร์ เรียกครัว เช็คโต๊ะงานเดียวต่อหน้าจอ นิ้วโป้งเอื้อมถึง
ครัว / บาร์แท็บเล็ตติดผนัง (มักเป็น iPad เก่า)ดูคิว กดรับ/เสร็จ ปฏิเสธของหมดตัวใหญ่ อ่านจากระยะ 1–2 เมตร ไม่ต้องล็อกอินซ้ำ
ลูกค้ามือถือตัวเองสแกน QR สั่ง ขอเพลง เรียกพนักงานส่วนนี้ทำมาดีแล้ว (mobile-first อยู่แล้ว)

ข้อสรุปที่เปลี่ยนวิธีคิด: “ผู้ใช้” ไม่ใช่คนเดียวกัน การพยายามให้ทุกหน้าทำงานดีเท่ากันบนทุกอุปกรณ์ คือรากของความซับซ้อนที่ทำให้ระบบใช้งานยาก
ทางที่ถูกคือ ประกาศให้ชัดว่าหน้าไหนออกแบบเพื่ออุปกรณ์ไหน แล้วให้ระบบพาผู้ใช้ไปหน้าที่เหมาะกับเครื่องที่ถืออยู่ — ไม่ใช่ยัดทุกอย่างลงทุกจอ

4.3 ซ่อนสิ่งที่เครื่องนี้ทำไม่ได้

  • บนมือถือ: ไม่ต้องโชว์เมนูที่ทำงานจริงไม่ได้บนจอเล็ก (ตั้งค่าภาษี/สร้าง payroll/แก้ผังโต๊ะ) — แสดงเป็น “เปิดบนคอมพิวเตอร์” พร้อมปุ่มส่งลิงก์ไปเมล แทนที่จะให้เข้าไปแล้วใช้ไม่ได้
  • บนแท็บเล็ตครัว: โหมดเต็มจอ ไม่มี sidebar ตัวใหญ่ ไม่หลุดล็อกอิน
  • รวมกับ stores.setup_profile จาก v1 (ซ่อนโมดูลที่ร้านนี้ไม่ใช้) → เมนูล่างบนมือถือจะสั้นลงจริง ไม่ต้องเลื่อนหา

F0 ทั้งหมดนี้ไม่ใช้ AI เลย — เป็นงาน UX/CSS/routing ล้วน ๆ แต่เป็นตัวที่แก้ “ระบบใช้งานยากบนหลายอุปกรณ์” ได้ตรงที่สุด และถ้าไม่ทำก่อน ฟีเจอร์ AI ทุกตัวจะไปนั่งอยู่บนหน้าจอที่ยังใช้ลำบากอยู่ดี

5. F2 Device Copilot — ฉบับรู้จักแพลตฟอร์ม

// modules/devices/capability.ts
detectCapabilities() -> {
  formFactor:  "mobile" | "tablet" | "desktop",
  os:          "windows" | "android" | "ios" | "macos" | "other",
  runtime:     "storeos-app" | "browser",     // จาก isNativePlatform() + userAgent "StoreOSApp"
  browser:     "chrome" | "edge" | "safari" | "firefox" | "other",
  webBluetooth, webUsb, nativeBle: boolean,
  printHub:    "online" | "offline" | "not-installed",
  appAvailable: "android" | "none",           // ★ iOS = none จนกว่าจะ ship
}

มี marker พร้อมใช้อยู่แล้ว: appendUserAgent: "StoreOSApp" ใน capacitor.config.ts และ isNativePlatform() ใน native-print-client.ts

ตัวอย่างข้อความจริงที่ผู้ใช้จะเห็น

iPad

“iPad ต่อเครื่องพิมพ์บลูทูธตรง ๆ ไม่ได้”
Safari ไม่รองรับ และ StoreOS ยังไม่มีแอปสำหรับ iPad
→ ใช้ Print Hub บนคอมที่เปิดค้างในร้าน [ติดตั้ง Print Hub]
→ หรือเครื่องพิมพ์ที่ต่อสาย LAN [ตั้งค่า IP]

Android ในเบราว์เซอร์

“ต่อบลูทูธได้เลย” [เชื่อมต่อ]
แนะนำติดตั้งแอป StoreOS เพื่อให้แจ้งเตือนเด้งตอนปิดจอด้วย [ดาวน์โหลด APK]

Windows + Firefox

“Firefox ต่อเครื่องพิมพ์ตรง ๆ ไม่ได้”
→ เปิดหน้านี้ด้วย Chrome หรือ Edge [คัดลอกลิงก์]
→ หรือใช้ Print Hub บนเครื่องนี้ [ติดตั้ง]

คลังความรู้อุปกรณ์ต้องแยกตามแพลตฟอร์ม

ตาราง device_profiles จาก v1 ต้องมี platform เป็นส่วนหนึ่งของคีย์ — เพราะเครื่องพิมพ์รุ่นเดียวกันตั้งค่าคนละแบบเมื่อผ่าน Web BT / native BLE / Print Hub (chunk size, service UUID, จังหวะการส่ง ต่างกันจริงตามที่เห็นใน bluetooth-client.ts ที่ต้องส่งทีละ 120 ไบต์ทุก 12ms)

6. เรื่อง iOS ต้องตัดสินใจแยก (ไม่ใช่งาน AI)

ทาง A — ทำ Print Hub ให้ติดตั้งง่ายที่สุด แนะนำทำก่อน

ยอมรับว่า iPad = Print Hub แล้วลงแรงกับ Hub ให้เต็มที่: ตัวติดตั้งคลิกเดียว, ค้นหา Hub ในวงแลนอัตโนมัติ, แสดงสถานะออนไลน์/คิวค้างในหน้า /settings/devices, auto-start ตอนเปิดเครื่อง

ของมีอยู่แล้ว: print-hub.ts, scripts/print-hub.mjs, build-print-hub-zip.mjs — เหลืองาน UX เป็นหลัก

ทาง B — ปล่อยแอป iOS จริง

ปลดล็อก BLE + push บน iPad/iPhone ครบเหมือน Android
ต้องใช้ Codemagic (build บน Windows ไม่ได้) + Apple Developer 99 USD/ปี + รอบรีวิว App Store

คุ้มถ้าลูกค้าใช้ iPad เป็นสัดส่วนมาก — แต่เป็นงาน infra ยาว ควรวางแผนแยกไม่ปนกับรอบนี้

คำถามที่ต้องรู้ก่อน: ลูกค้าจริงตอนนี้ใช้ iPad กี่ร้าน? ถ้ายังน้อย ทาง A พอ ถ้าเยอะ ทาง B คือของที่เลี่ยงไม่ได้ — ข้อมูลนี้ดูได้จาก user agent ใน log หรือถามฝ่ายขายโดยตรง

8. ต้องตัดสินใจ

  1. ลูกค้าจริงใช้ iPad กี่ร้าน? — ตัวชี้ว่าจะลงแรงกับ Print Hub (ทาง A) หรือต้องปล่อยแอป iOS (ทาง B)
  2. เริ่มที่ เฟส 0.1 (จอแท็บเล็ต/POS) หรือ เฟส 2 (Device Copilot) ก่อน — ข้อแรกกระทบผู้ใช้ปัจจุบันทุกวัน ข้อหลังกระทบตอนติดตั้งครั้งแรก
  3. ยอมเปลี่ยนจุดตัด POS จาก 1024 → 768 ไหม (ต้องทดสอบกับ iPad จริงก่อน deploy)
  4. เพดานค่าโมเดลต่อร้านต่อเดือน (ค้างจาก v1)
