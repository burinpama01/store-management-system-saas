1. คำปลุกไทยจับได้จริงไหม

วิธีวัด: สังเคราะห์เสียงคำปลุกด้วย Microsoft Pattara (th-TH) ซึ่งเป็นเสียงไทยจริงที่ติดมากับ Windows 11 แล้วยิงไฟล์เสียงเข้า recognizer en-US ที่โหลดไวยากรณ์คำปลุกไว้ ทำซ้ำที่ความเร็วพูด 6 ระดับ

คำปลุก0.800.850.900.951.001.20
ฮัลโหลโอเอส0.900.71––––
เฮลโหลโอเอส0.930.90–0.83––
หวัดดีโอเอส0.990.98––––
สวัสดีโอเอส0.990.98––––
Hello OS (อังกฤษ)0.990.990.990.990.990.99

ตัวเลข = ความมั่นใจของ engine, “–” = ไม่จับเลย · เกณฑ์ปลุกที่ตั้งไว้คือ 0.72

เส้นแบ่งอยู่ระหว่าง 0.85 กับ 0.90 อย่างคมชัด ทั้งสี่คำ — ไม่ใช่การค่อย ๆ แย่ลง แปลว่า recognizer อังกฤษรับลำดับเสียงไทยได้เฉพาะเมื่อพูดแบบตั้งใจชัดถ้อยชัดคำ (ประมาณช้ากว่าที่คนพูดปกติ 15–20%)

สิ่งที่ตัดออกไปแล้วว่าไม่ใช่สาเหตุ:

  • ไม่ใช่รูปแบบไฟล์ — เสียงอังกฤษจากท่อเดียวกัน (WinRT TTS 16kHz mono) จับได้ 0.99 ทุกความเร็ว
  • ไม่ใช่ความเงียบนำหน้า — เติมความเงียบหัวท้าย 300ms แล้วผลไม่เปลี่ยนแม้แต่หลักที่สาม
  • ไม่ใช่หน่วยเสียงเพี้ยน — ลองเพิ่มรูปการออกเสียงแบบลดรูป (ow ey s, ตัดพยางค์) แล้วไม่ช่วย

2. ปลุกผิดจากคำทักทายปกติ

ชุดทดสอบด้านลบ 10 ประโยคที่พนักงานพูดจริง สังเคราะห์ด้วยเสียงไทยเช่นกัน

ประโยคก่อนใส่คำล่อหลังใส่คำล่อ
“หวัดดีครับพี่”ปลุกผิด watdee_os 0.84ไม่ปลุก ตกที่กฎคำล่อ 0.78
อีก 9 ประโยค (เพิ่มกาแฟเย็นสองแก้ว, เช็คบิลโต๊ะห้า, สวัสดีค่ะรับอะไรดีคะ, ฮัลโหลได้ยินไหม, โอเคครับ …)ไม่ปลุกไม่ปลุก
วิธีที่ได้ผลคือให้เสียงมีที่ลงที่ตรงกว่า (ไวยากรณ์คำล่อ) ไม่ใช่การดันเกณฑ์ความมั่นใจ — ถ้าดันเกณฑ์ขึ้นเป็น 0.85 เพื่อกัน “หวัดดีครับพี่” คำว่า “ฮัลโหลโอเอส” (0.71) จะหลุดทันที

3. ส่งไมค์ต่อ 100 รอบ

จำลองฝั่งเว็บด้วย recognizer ตัวที่สองที่แย่งเปิดไมค์ตัวเดียวกัน — ถ้า native ยังไม่ปล่อยจริง ตัวที่สองจะเปิดไม่ได้

ตัวชี้วัดค่า
รอบที่สำเร็จ100 / 100
native ปล่อยไมค์ (p95)0.30 ms
ฝั่งเว็บเปิดไมค์ได้ (p95)12.55 ms
native ขอไมค์คืน (p95)12.93 ms
บั๊กที่เจอระหว่างทาง และเป็นเหตุผลว่าทำไม spike นี้คุ้ม: รอบแรกล้มเหลว 90/100 ด้วยข้อความ “Cannot perform this operation while the recognizer is doing recognition.” เพราะ RecognizeAsyncCancel() เป็นงานแบบไม่รอ — ต้องรออีเวนต์ RecognizeCompleted ก่อนจึงจะปล่อยอุปกรณ์ได้จริง ถ้า native host ตัวจริงเขียนแบบแรก ไมค์จะค้างเป็นระยะโดยหาสาเหตุไม่เจอ

4. สัญญาข้อความและ watchdog

ทำครบทั้งสองฝั่งแล้ว พร้อมเทสต์ที่บังคับกฎความปลอดภัย

สิ่งที่ทำที่อยู่เทสต์
สัญญาฝั่ง native + watchdogwindows/StoreOS.VoiceSpike/21 เทสต์ (xUnit) ผ่านหมด
สัญญาฝั่งเว็บ + สะพานรับข้อความsrc/modules/voice-pos/standby-contract.ts15 เทสต์ (vitest) ผ่านหมด

กฎที่ถูกล็อกด้วยเทสต์:

  • watchdog (9s) ต้องมากกว่า หน้าต่างฟังของเว็บ (6s) — constructor โยน error ถ้าตั้งผิด
  • multi-turn ต่อเวลาได้ถึง 15 วินาที แต่ถูกตัดที่เพดานรวม 20 วินาทีเสมอ
  • sessionStarted ที่มาช้าหลัง watchdog ตัดไปแล้ว ต้องถูกทิ้ง (ไม่ใช่เปิด session ย้อนหลัง)
  • ฟิลด์ intent / transcript / command ที่แนบมากับข้อความ native ถูกตัดทิ้งเสมอ
  • เปิดไมค์เองไม่ได้ = แสดงปุ่มให้ผู้ใช้แตะ ห้ามสร้างคลิกปลอม

6. ข้อสรุปที่เปลี่ยนจาก v1

คำปลุกภาษาไทยบน Windows ทำได้จริง — ไม่ต้องมี recognizer ภาษาไทย ไม่ต้องใช้บริการคลาวด์ ใช้หน่วยเสียง SAPI ของ en-US เขียนเองบวกไวยากรณ์คำล่อก็พอ
แต่ต้องพูดช้าและชัด ซึ่งเปลี่ยนหน้าตาฟีเจอร์: ต้องบอกผู้ใช้ตรง ๆ ว่าให้พูดคำปลุกแบบชัดถ้อยชัดคำ และต้องคง push-to-talk ไว้เป็นทางหลักเสมอ ไม่ใช่ทางสำรอง
ทางเลือกที่ควรพิจารณาถ้าอยากให้พูดเร็วได้: ให้ร้านเลือก “Hello OS” เป็นคำปลุกเริ่มต้น (จับได้ทุกความเร็ว 0.99) แล้วให้คำไทยเป็นตัวเลือกเสริม
สิ่งที่ยังไม่เปลี่ยน: ลำดับใน Rollout Order — Phase 6 (Voice บนเครื่องร้าน) ยังต้องรอ Phase 5 (pilot Print Hub 21 วัน) และตอนนี้ยังไม่ผ่าน: 21 วันล่าสุดมีงานพิมพ์แค่ 25 ใบ ล้มเหลว 64% และมี log จากเครื่องร้านแค่ 2 วัน (ดู npm run pilot:print-hub)
