บิลรวมโต๊ะ: 1 โต๊ะ = 1 บิล = 1 การจ่าย

แผน v2 · 2026-09-18 · ต่อจาก v1 (PR #62) + ผลรีวิว storeos_pr62_review.md · สถานะ: รออนุมัติ

1. สิ่งที่เปลี่ยนจาก v1

v1 ให้ตั๋วโต๊ะ ผูก กับออเดอร์ QR แล้วตอนจ่ายเก็บเงินแยกทีละออเดอร์ (หลายรายการจ่าย) — ผู้ใช้ยืนยันว่า ไม่ต้องการแบ่งเงิน: ลูกค้าจ่ายก้อนเดียว ต้องไล่ตรวจเงินย้อนหลังได้ว่าก้อนนี้มาจากรายการไหน ก่อนจ่ายพนักงานต้อง พิมพ์รายการให้ลูกค้าเช็ค และ แก้ไขได้ก่อนกดชำระจริง

v2 จึงเปลี่ยนเป็น รวมเป็นบิลเดียวตอนชำระ แล้วจ่ายผ่านหน้าจ่ายเงินปกติของ POS (เงินสด / Beam / TrueMoney / พร้อมเพย์ ตามนโยบายเดียวกับ POS)

2. Flow ใหม่ (มุมพนักงาน)

  1. เปิดโต๊ะ → พิมพ์ QR + ระบบเปิดตั๋วโต๊ะรอไว้ (เหมือน v1 แต่สร้างแบบ atomic)
  2. ลูกค้าสั่ง QR → เข้าครัวตามปกติ → โผล่ในตั๋วโต๊ะ (เหมือน v1)
  3. พนักงานเพิ่มรายการในตั๋วได้
  4. พิมพ์ใบตรวจรายการ (ยังไม่ชำระ) — รวมรายการ QR + รายการหน้าร้าน + ยอดรวมทั้งโต๊ะ ให้ลูกค้าเช็ค
  5. แก้ไขก่อนจ่าย: รายการหน้าร้านแก้ในตะกร้าตามปกติ · รายการ QR กด "ยกเลิกรายการ" (ใช้ void_qr_order_item ที่มีอยู่ ต้องใส่เหตุผล มี log)
  6. กด ชำระเงิน → server รวมบิลโต๊ะ เป็นออเดอร์เดียว → เข้าหน้าจ่ายเงินปกติของ POS ด้วยยอดทั้งโต๊ะ
  7. จ่ายสำเร็จ (Beam ยืนยัน PAID ฝั่ง server / เงินสด) → ใบเสร็จใบเดียว → ปิดโต๊ะ + ลบตั๋ว

3. การรวมบิล (หัวใจของ v2)

RPC ใหม่ consolidate_table_bill (security definer, เช็คสิทธิ์ cashier ในร้าน, idempotent ด้วย operation key) ทำใน transaction เดียว:

lock โต๊ะ + ออเดอร์ QR ที่เปิดอยู่ของโต๊ะ (for update)
สร้างออเดอร์บิลรวม 1 ใบ (ผูกโต๊ะ, channel = table_bill)
ย้าย order_items ของทุกออเดอร์ QR ของโต๊ะ → ออเดอร์บิลรวม   (สถานะครัวรายรายการคงเดิม)
เพิ่มรายการจากตั๋ว (ราคาจาก catalog ฝั่ง server) + ตัดสต็อกรายการเหล่านี้ทันที
ออเดอร์ QR เดิม → cancelled + merged_into_order_id  (ไม่คืนสต็อก เพราะรายการย้ายไปแล้ว)
คำนวณยอดใหม่ + ส่วนลดท้ายบิลของตั๋ว (ผ่าน discount policy เดิม)

จากนั้นใช้ collectPaymentAction เดิมกับออเดอร์บิลรวม → Beam ยังเป็น 1 การจ่าย : 1 ออเดอร์ ตามโมเดลเดิม ไม่ต้องแก้ระบบ Beam

ทำไมออกแบบแบบนี้

  • สต็อกคิดระดับออเดอร์ (qr_order_source): ออเดอร์ QR ตัดตอนสั่ง ออเดอร์ POS ตัดตอนจ่าย — บิลรวมตั้ง qr_order_source = true (จ่ายแล้วไม่ตัดซ้ำ) และตัดสต็อกรายการจากตั๋วตอนรวมบิล จึงไม่ต้องแก้ RPC ชำระเงิน 3 ตัว (close_pos_order_payment, stock pool, unified)
  • ย้าย order_items (ไม่คัดลอก) → ประวัติครัว/สถานะรายรายการ/stock pool snapshot ติดไปด้วย ตรวจย้อนหลังได้ว่ารายการมาจาก QR ออเดอร์ไหน (merged_into_order_id)
  • ถ้ามีออเดอร์ QR เข้ามา หลัง รวมบิล → ยังเป็นออเดอร์เปิดของโต๊ะ ระบบจะไม่ปิดโต๊ะและแจ้งให้เก็บเพิ่ม

4. แก้ตามรีวิว PR #62

ข้อรีวิวทางแก้ใน v2
🔴 Table Bill ใช้ PromptPay manual แทน Beamชำระผ่านหน้าจ่ายเงินปกติของ POS → นโยบายเดียวกัน (ซ่อนพร้อมเพย์เมื่อร้านใช้ Beam, Beam ต้อง PAID ฝั่ง server) · TableBillModal เดิมในเส้นทางตั๋วโต๊ะไม่ใช้แล้ว (เมนู "เช็คบิลโต๊ะ" เดิมยังอยู่สำหรับโต๊ะเก่า — จะปรับให้ส่งเข้าเส้นทางเดียวกัน)
🔴 จ่ายตั๋วอย่างเดียวแล้วโต๊ะยัง occupiedตั๋วโต๊ะทุกใบจ่ายผ่านเส้นทางบิลรวมเสมอ (ไม่มี QR ก็ใช้เส้นทางเดียวกัน) → จ่ายแล้วปิดโต๊ะ + ลบตั๋ว ฝั่ง server
🔴 สร้างตั๋วไม่ atomic + query limit 30คอลัมน์ ticket_source (manual | table_auto) + unique index บางส่วน "1 ตั๋วอัตโนมัติต่อโต๊ะ" + RPC ensure_table_auto_ticket (insert … on conflict do nothing แล้วคืนใบเดิม) · query ตั๋วตามโต๊ะแยก ไม่มี limit (UI ยัง limit 30 ได้)
🟠 log ล้มแล้วเปลี่ยนผลเปิดโต๊ะlogSystemEvent ไม่ throw อยู่แล้ว (มี try/catch ภายใน) แต่จะห่อ safeLog ให้ชัดเจน + test
🟡 ลบตั๋วว่างไม่มี auditlog tableId / ticketId / สำเร็จ-ล้ม / เหตุผล
🟠 test เป็น source-stringย้ายตรรกะเป็น service รับ dependency → unit test พฤติกรรมจริง + SQL integration test (ต้องเปิด Docker + supabase start) สำหรับ concurrency / >30 ตั๋ว / รวมบิล / สต็อกไม่ตัดซ้ำ

5. Migration (additive ทั้งหมด)

  • pos_saved_tickets.ticket_source text default 'manual' + unique index บางส่วน
  • orders.merged_into_order_id uuid (nullable, FK orders)
  • RPC ensure_table_auto_ticket, consolidate_table_bill
  • stores.table_open_auto_ticket (จาก v1)

6. ความเสี่ยง / ต้องยอมรับ

  • ระบบเงิน + สต็อก + DB ตัวเดียวกับ prod — RPC รวมบิลต้องทดสอบบน Supabase local ก่อน apply
  • รายงาน QR vs POS: บิลรวมนับเป็นช่องทาง "บิลรวมโต๊ะ" — รายงานที่แยกด้วย qr_order_source ต้องปรับให้เห็นช่องทางนี้
  • ครัว: ย้ายรายการตอนจ่าย ปกติอาหารเสิร์ฟแล้ว ถ้ายังมีรายการครัวทำไม่เสร็จ จะเตือนก่อนรวมบิล (สถานะรายรายการคงเดิม)
  • ร้าน Unified POS (นำร่อง 3 ร้าน) ไม่ใช้ PosTerminal จึงไม่กระทบ
  • ขนาดงานใหญ่กว่า v1 มาก — ประเมิน 1–2 วันทำงาน รวม test

7. ลำดับงาน

  1. Migration + RPC + SQL integration test บน Supabase local
  2. Service ฝั่ง TS (ensure ticket, consolidate, finish table) + unit test พฤติกรรม
  3. POS: พิมพ์ใบตรวจรายการรวม QR · ยกเลิกรายการ QR · ปุ่มชำระ → รวมบิล → หน้าจ่ายเงินปกติ
  4. ปรับรายงานช่องทาง
  5. Verify ครบ (tsc / test / lint / build / Supabase local e2e) → อัปเดต PR #62
