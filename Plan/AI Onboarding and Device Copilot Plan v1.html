0. ข้อเท็จจริงที่ต้องยอมรับก่อนวางแผน

AI ไม่ได้แก้ปัญหา “ใช้งานยาก” โดยตัวมันเอง — จากการอ่านโค้ดจริง ปัญหาแรงเสียดทานของ StoreOS ส่วนใหญ่เป็น ปัญหา UX ที่แก้ได้ด้วยตรรกะธรรมดา ถ้าเอา AI ไปแปะทับ UX ที่ยังสับสน จะได้แค่แชทที่ผู้ใช้ไม่กล้าเชื่อ และค่าโมเดลที่จ่ายฟรี

แผนนี้จึงแบ่งงานเป็น 2 ชั้นเสมอ และ ชั้นที่ 1 ต้องเสร็จก่อนชั้นที่ 2 ทุกครั้ง:

ชั้นที่ 1 — Deterministic (ไม่ใช้ AI)

ตรวจสถานะจริง, ตัดตัวเลือกที่ใช้ไม่ได้ทิ้ง, เขียนข้อความ error ให้เป็นภาษาคน, ให้ปุ่มลัดที่แก้ปัญหาได้เลย
แก้แรงเสียดทานได้ราว 60–70% ด้วยต้นทุน 0 บาท/ครั้ง และไม่มีทางตอบมั่ว

ชั้นที่ 2 — AI

รับเฉพาะเคสที่ตรรกะตายตัวเอาไม่อยู่: อ่านรูปเมนู, เดารุ่นเครื่องพิมพ์จากรูป, วินิจฉัยอาการแปลก ๆ, เข้าใจคำถามภาษาคน
ตรงนี้ AI คุ้มจริงเพราะทำแทนไม่ได้

1. จุดเจ็บจริงที่พบในโค้ดปัจจุบัน

จุดสภาพตอนนี้ผลต่อผู้ใช้ใหม่
src/app/onboarding/page.tsx เป็นลิงก์ 4 อันแบบ static — ไม่รู้เลยว่าผู้ใช้ทำขั้นไหนไปแล้ว ไม่มี progress กดออกไปแล้วกลับมาไม่ได้ ไม่รู้ว่าเหลืออะไร ไม่รู้ว่า “พร้อมขายหรือยัง” → หลุดตั้งแต่วันแรก
การเพิ่มเมนู (/catalog) คีย์มือทีละรายการ: หมวด → สินค้า → variant → modifier ร้าน 150 เมนู = หลายชั่วโมง → สาเหตุอันดับ 1 ที่ทดลองแล้วไม่ไปต่อ
เชื่อมเครื่องพิมพ์ ตาราง printers มี 5 type (browser/usb/bluetooth/ip/escpos) + Print Hub + native BLE รวมเป็น อย่างน้อย 6 เส้นทาง ให้ผู้ใช้เลือกเอง ผู้ใช้ไม่มีทางรู้ว่าเครื่องตัวเองใช้ทางไหน → ลองผิดลองถูกจนเลิก
ข้อความ error ของอุปกรณ์ “ไม่พบช่องเขียนข้อมูลของเครื่องพิมพ์ (characteristic)”, “เบราว์เซอร์นี้ไม่รองรับ WebUSB (ใช้ Chrome/Edge เดสก์ท็อป)” ถูกต้องทางเทคนิค แต่ไม่บอกว่าต้องทำอะไรต่อ → โทรหาซัพพอร์ต
iPad / มือถือ WebView ไม่มี Web Bluetooth/WebUSB → ต้องใช้แอป StoreOS หรือ Print Hub เท่านั้น (โค้ดรู้ผ่าน isNativePlatform()) ระบบรู้อยู่แล้วว่าทางนั้นใช้ไม่ได้ แต่ยังปล่อยให้ผู้ใช้กดแล้วเจอ error
เมนูระบบ 30 โมดูล, /settings มี 14 หน้าย่อย หาไม่เจอว่าตั้งค่าที่ไหน

3. F1 — Setup Copilot (เปลี่ยน onboarding ให้มีชีวิต)

ตอนนี้

“ทำตามขั้นตอนด้านล่าง” + ลิงก์ 4 อันที่ไม่เคยเปลี่ยนสถานะ ต่อให้ทำครบแล้วก็ยังหน้าตาเดิม

หลังทำ

“ร้านคุณพร้อมขายแล้ว 60% — เหลืออีก 2 ขั้น” พร้อมสถานะจริงต่อขั้น และปุ่มลัดที่ทำให้เสร็จได้ในหน้าเดียว

3.1 คำนวณความพร้อมจากข้อมูลจริง (ไม่ใช้ AI)

ฟังก์ชันใหม่ getStoreReadiness(storeId) อ่านของที่มีอยู่แล้วทั้งหมด ไม่ต้องเพิ่มตาราง:

ขั้นเช็คจากถือว่าเสร็จเมื่อ
ข้อมูลร้านstoresมีชื่อ + timezone + ที่อยู่หรือเบอร์โทร
เมนูสินค้าproducts, categoriesมีสินค้า active ≥ 5 รายการ
ช่องทางขายtables / โหมดร้านมีโต๊ะ ≥ 1 (ถ้าเป็นร้านนั่งทาน) หรือข้ามได้ถ้าเป็นขายส่ง/หน้าร้าน
อุปกรณ์printers, print_jobsมีเครื่องพิมพ์ที่ทดสอบพิมพ์ผ่านแล้ว (ไม่ใช่แค่บันทึกค่า)
ทีมงานmembershipsมีสมาชิก ≥ 2 หรือกดข้าม (ร้านเจ้าของคนเดียว)
ขายจริงordersมีบิลแรกแล้ว ← เป้าหมาย activation ที่แท้จริง

นิยาม activation ของโปรเจกต์นี้: ร้านใหม่ปิดบิลจริงบิลแรกภายใน 7 วันหลังสมัคร — ทุกอย่างในแผนนี้วัดผลด้วยตัวเลขนี้ตัวเดียว

3.2 ถาม 3 คำถาม แล้วตั้งค่าให้

ตอนเข้าครั้งแรก ถามสั้น ๆ: ขายอะไร (ร้านอาหาร / คาเฟ่ / บุฟเฟต์ / ขายส่ง / มินิมาร์ท) · ลูกค้าสั่งยังไง (พนักงานคีย์ / ลูกค้าสแกน QR / เดลิเวอรี) · กี่สาขา

  • คำตอบ → เก็บลง stores.setup_profile (jsonb, migration เล็ก) → ใช้ซ่อนเมนูที่ร้านนี้ไม่ใช้ ในแถบข้าง (แก้ “ระบบใช้งานยาก” ได้ตรงที่สุด)
  • เตรียม preset ตายตัวต่อประเภทร้าน (หมวดหมู่เริ่มต้น, จำนวนโต๊ะ, เปิด/ปิดโมดูล) — เขียนเป็นค่าคงที่ ไม่ต้องใช้ AI
  • ชั้น AI (ทีหลัง): ผู้ใช้พิมพ์อธิบายร้านตัวเองอิสระ → เสนอ preset ที่เหมาะกว่า preset สำเร็จรูป

3.3 ปุ่ม “ให้ AI ทำให้”

ทุกขั้นที่ยังไม่เสร็จ มีทางลัดในหน้าเดียว ไม่ต้องเด้งไปหน้าอื่น: สร้างหมวดหมู่เริ่มต้น · สร้างโต๊ะ 1–10 · ตั้งเวลาเปิด-ปิดร้าน · เชิญทีมด้วยลิงก์เดียว

กติกา: ทุกปุ่มแสดง preview สิ่งที่จะถูกสร้างก่อนเสมอ และต้องมีปุ่มเลิกทำ (undo) ภายใน session นั้น ผู้ใช้ใหม่จะกล้ากดก็ต่อเมื่อรู้ว่ากดผิดแล้วย้อนได้

4. F2 — Device Copilot (หัวใจของรอบนี้)

ทำเป็นหน้าใหม่ /settings/devices ที่รวมอุปกรณ์ทุกชนิดไว้ที่เดียว แล้วให้ /settings/receipt · /settings/kitchen · /settings/print-hub ลิงก์เข้ามา

4.1 ชั้นที่ 1 — ตรวจสภาพแวดล้อมแล้ว “ตัดตัวเลือกที่ใช้ไม่ได้ทิ้ง”

แทนที่จะให้ผู้ใช้เลือกจาก 6 เส้นทาง ระบบตรวจเองก่อนว่าเครื่องที่กำลังใช้อยู่ทำอะไรได้:

// modules/devices/capability.ts  (ไม่มี AI, เทสต์ได้ 100%)
detectCapabilities() -> {
  platform:      "native-app" | "desktop-browser" | "mobile-browser" | "ipad-safari",
  webBluetooth:  boolean,   // navigator.bluetooth + secure context
  webUsb:        boolean,   // navigator.usb (เดสก์ท็อป Chrome/Edge เท่านั้น)
  nativeBle:     boolean,   // isNativePlatform() จาก native-print-client
  printHub:      "online" | "offline" | "not-installed",
  lan:           boolean,
}

แล้วแสดงผลแบบนี้ — เหลือทางเลือกที่ใช้ได้จริงแค่ 1–2 ทาง พร้อมเหตุผล:

ตอนนี้ (iPad)

ผู้ใช้เห็นปุ่ม “เชื่อมต่อ Bluetooth” → กด → “เบราว์เซอร์นี้ไม่รองรับ Web Bluetooth (ใช้ Chrome/Edge)” → จบ ไม่รู้ต้องทำอะไรต่อ

หลังทำ (iPad)

“iPad เชื่อมเครื่องพิมพ์บลูทูธตรง ๆ ไม่ได้ (ข้อจำกัดของ Safari) — คุณมี 2 ทาง”
① ติดตั้งแอป StoreOS แล้วเชื่อมผ่านแอป [ดาวน์โหลด]
② ใช้ Print Hub บนคอมที่เปิดค้างไว้ [ติดตั้ง Print Hub]
แนะนำ ② เพราะร้านคุณมี 3 จุดพิมพ์

ข้อนี้สำคัญที่สุดในเอกสาร: แก้ปัญหาเชื่อมอุปกรณ์ได้มากที่สุดในบรรดาทั้งแผน แต่ ไม่ใช้ AI เลยสักบรรทัด — เป็นตรรกะตายตัวที่เขียน unit test ได้ครบ และไม่มีวันตอบมั่ว

4.2 ชั้นที่ 2 — AI เข้ามาตรงไหน

D1. แปล error เป็นวิธีแก้ทีละขั้น

ส่งบริบทที่มีจริง (error code, ช่องทาง, platform, ยี่ห้อ/รุ่นถ้ารู้, ผลลัพธ์ที่พยายามมาแล้ว) → ได้คำตอบภาษาไทยที่ทำตามได้ + ปุ่มลัดจริง (ลองใหม่ / สลับช่องทาง / เปิดหน้าติดตั้ง Hub)

ต่อกับ error ที่มีอยู่แล้วใน bluetooth-client.ts, usb-client.ts, network-print-client.ts

D2. ถ่ายรูปเครื่องพิมพ์ / ฉลากใต้เครื่อง → รู้รุ่น

Vision อ่านยี่ห้อ-รุ่น → เติมให้อัตโนมัติ: paper_width (58/80mm), ประเภทการเชื่อม, ชื่อ BLE ที่คาดว่าจะเจอ, ค่า usb_vendor_id ที่พบบ่อย → ผู้ใช้แค่กดยืนยัน

ครอบคลุมกรณีที่ผู้ใช้ตอบไม่ได้ว่า “เครื่องพิมพ์รุ่นอะไร”

D3. สแกนสติกเกอร์ IP / QR ของเครื่องพิมพ์เครือข่าย

ถ่ายรูปหน้าจอ self-test ที่เครื่องพิมพ์ปริ้นออกมา → ดึง IP/port/MAC ไปเติมฟอร์ม แทนการให้ผู้ใช้พิมพ์เลข IP เอง

D4. วินิจฉัยจาก “ผลพิมพ์จริง”

หลังพิมพ์ทดสอบ ถาม 4 ตัวเลือก: ออกปกติ / กระดาษว่าง / ภาษาไทยเป็นตัวขยะ / ตัวหนังสือล้นขอบ → แต่ละอาการ map ไปสาเหตุที่ระบบรู้อยู่แล้ว (raster fallback, code page, paper_width ผิด) แล้วแก้ให้อัตโนมัติแล้วพิมพ์ซ้ำ

ระบบมี escpos-raster.ts อยู่แล้ว = แก้อาการภาษาไทยเพี้ยนได้จริง

4.3 ตัวคูณระยะยาว — คลังความรู้อุปกรณ์

ทุกครั้งที่มีร้านเชื่อมสำเร็จ บันทึกสูตรที่ใช้ได้ลงตารางกลางระดับแพลตฟอร์ม:

device_profiles
  brand, model            -- เช่น 'Xprinter', 'XP-58IIH'
  platform                -- native-app / desktop-chrome / print-hub
  channel                 -- native-bluetooth / bluetooth / usb / ip
  settings   jsonb        -- paper_width, service uuid, chunk size, ฯลฯ
  success_count, fail_count
  verified_by_admin  bool

ผลลัพธ์

ร้านถัดไปที่ใช้เครื่องรุ่นเดียวกัน จะได้ “เครื่องนี้เคยตั้งสำเร็จมาแล้ว 34 ร้าน — ตั้งค่าให้เลยไหม” แล้วจบใน 1 คลิก โดยไม่ต้องเรียกโมเดลเลย

ทำไมถึงคุ้ม

ยิ่งมีร้านใช้มาก ระบบยิ่งเชื่อมอุปกรณ์เก่ง และค่า AI ยิ่งถูกลง (เพราะเคสส่วนใหญ่ตกลงมาที่ cache) — เป็นคูเมืองที่คู่แข่งลอกไม่ได้เพราะไม่มีข้อมูล

4.4 ขยายไปอุปกรณ์อื่นในหน้าเดียวกัน

อุปกรณ์ทำอะไรของที่มีอยู่แล้ว
เครื่องพิมพ์ใบเสร็จ/ครัวตรวจ + ทดสอบ + วินิจฉัย + ผูกกับ kitchen stationprinters, kitchen_stations, station-routing.ts
ลิ้นชักเก็บเงินปุ่ม “ทดสอบเปิดลิ้นชัก” + บอกว่าต้องเสียบสาย RJ11 เข้าเครื่องพิมพ์ ไม่ใช่คอมESC/POS kick — ต้องเพิ่ม
เครื่องอ่านบาร์โค้ดช่องทดสอบ “ยิงบาร์โค้ดใส่ช่องนี้” → ยืนยันว่าอ่านได้ + ตั้ง suffix ให้ถูกcatalog_barcodes, jsqr
จอลูกค้าทดสอบเปิดจอที่สอง + คิวอาร์จับคู่customer_display_settings
Print Hubตรวจว่า agent ออนไลน์ไหม + คิวค้างกี่งาน + ดาวน์โหลดตัวติดตั้งprint_hub.ts, build-print-hub-zip.mjs
มือถือพนักงานตรวจว่า push token ลงทะเบียนแล้วหรือยัง + ปุ่มส่งทดสอบdevice_push_tokens

5. F3 — Menu Scan → Catalog

1. อัปโหลดรูปเมนู/ป้ายราคา/PDF (หลายไฟล์)
2. AI แตกโครงหมวด → สินค้า → ราคา → ตัวเลือก
3. ผู้ใช้ตรวจตารางแก้ไขได้ ทีละหมวด กันซ้ำกับของเดิม
4. ยืนยันสร้างผ่าน catalog action เดิม + undo ทั้งชุดได้
  • ปล่อยให้ใช้ ฟรีตอน onboarding (เช่น 5 หน้าแรก) ทุกแพ็กเกจ — นี่คือค่าใช้จ่ายทางการตลาด ไม่ใช่ต้นทุนฟีเจอร์
  • ต้องไม่บังคับให้ถูก 100% — ตั้งเป้า “ถูก 80% แล้วผู้ใช้แก้ 20%” ก็ยังชนะการคีย์มือ 150 รายการอย่างขาดลอย
  • ราคาที่อ่านไม่ชัดให้ทำเป็นสีเหลืองบังคับให้ผู้ใช้ยืนยัน — ห้ามเดาราคาเงียบ ๆ

6. F4 — ผู้ช่วยในแอป & F5 — Activation Nudge

F4 · แถบคำสั่ง Ctrl/Cmd + K

ชั้นที่ 1: ค้นหาหน้า/สินค้า/พนักงานแบบ fuzzy ธรรมดา (แก้ปัญหา “หาเมนูไม่เจอ” ได้ทันที ไม่ต้องมี AI)

ชั้นที่ 2: พิมพ์เป็นประโยค “จะเปลี่ยนราคาข้าวผัดยังไง” / “เพิ่มโต๊ะอีก 5 โต๊ะ” → ตอบสั้น + พาไปหน้าที่ใช่ + เสนอ action ให้กดยืนยัน

ใช้ tool registry ชุดเดียวกับ Device Copilot

F5 · กระตุ้นตามความคืบหน้าจริง

  • วันที่ 1–14: ถ้ายังไม่ครบ → เตือนในแอป/LINE “เหลืออีก 2 ขั้นก็เปิดขายได้”
  • ฉลอง: บิลแรก · 100 บิลแรก · สรุปสัปดาห์แรก
  • ถ้าตั้งค่าอุปกรณ์ค้างเกิน 2 วัน → เสนอ Device Copilot ตรง ๆ

Vercel เป็น Hobby plan → cron ถี่ใช้ไม่ได้ (เคยทำ deploy ล้มมาแล้ว) ต้องเป็น cron วันละครั้ง

7. สถาปัตยกรรมและไฟล์ที่เกี่ยวข้อง

  usage.ts                // metering + quota ต่อ org (ตัดวงจรเมื่อเกินเพดาน)

  recommend.ts            // เลือกเส้นทางที่ควรใช้ + เหตุผลภาษาไทย
  profiles-repository.ts  // อ่าน/เขียน device_profiles

src/modules/onboarding/
  readiness.ts            // ★ คำนวณความพร้อมจากข้อมูลจริง

src/app/(dashboard)/settings/devices/   // หน้าใหม่ รวมอุปกรณ์ทุกชนิด
src/app/onboarding/                      // เขียนใหม่ให้รู้สถานะจริง

Migration ที่ต้องมี

  • stores.setup_profile jsonb — ประเภทร้าน/ช่องทางขาย (ใช้ซ่อนเมนูที่ไม่ใช้)
  • device_profiles — คลังความรู้อุปกรณ์ระดับแพลตฟอร์ม (ไม่ผูก org)
  • ai_usage_logs — org_id, feature, model, tokens, cost, created_at
  • เพิ่ม printers.last_test_ok_at, printers.brand, printers.model

บทเรียนจาก incident 2026-08-20: คอลัมน์ใหม่ทุกตัวต้องมี default ที่ทำให้แถวเดิมพฤติกรรมไม่เปลี่ยน และห้ามใช้ค่าที่ตีความได้สองแบบมาเป็นตัวชี้สิทธิ์ — เคยทำทั้งองค์กรหลุดสิทธิ์มาแล้ว

8. ลำดับการทำและการวัดผล

เฟสงานใช้ AI?แรงวัดผลด้วย
1F1 readiness + progress + preset ประเภทร้าน + ซ่อนเมนูที่ไม่ใช้ไม่3–4 วัน% ร้านใหม่ที่ตั้งค่าครบใน 3 วัน
2F2 ชั้นที่ 1: capability.ts + หน้า /settings/devices + ข้อความแนะทางที่ใช้ได้จริงไม่4–5 วัน% ร้านที่พิมพ์ทดสอบผ่านในครั้งแรก
3ฐาน modules/ai + ai_usage_logs + quotaฐาน1–2 วันต้นทุนต่อร้านต่อเดือนมองเห็นได้
4F2 ชั้นที่ 2: D1 แปล error, D4 วินิจฉัยผลพิมพ์, device_profilesใช่4–5 วันจำนวนเคสซัพพอร์ตเรื่องเครื่องพิมพ์
5F3 Menu Scanใช่5–6 วันเวลาเฉลี่ยจนมีสินค้า 20 รายการแรก
6F2 D2/D3 (สแกนรุ่น/IP) + F5 nudgeใช่3–4 วันอัตราปิดบิลแรกใน 7 วัน
7F4 ผู้ช่วย Ctrl+K2 ชั้น4–5 วันสัดส่วนการใช้ซ้ำ

สังเกต: เฟส 1–2 คือของที่แก้ปัญหาผู้ใช้ใหม่ได้มากที่สุด และ ไม่ต้องใช้ AI เลย — ถ้าเวลาจำกัด ทำแค่ 2 เฟสนี้ก็เปลี่ยนประสบการณ์ผู้ใช้ใหม่ไปแล้ว ส่วน AI ค่อยตามมาเสริมจุดที่ตรรกะตายตัวเอาไม่อยู่

9. กฎเหล็กของรอบนี้

  1. AI เสนอ ผู้ใช้ยืนยัน — ทุกอย่างที่เขียนข้อมูลต้องมี preview และย้อนกลับได้
  2. ห้าม LLM แตะ DB ตรง — ผ่าน tool ที่ห่อ repository เดิมเท่านั้น RLS + สิทธิ์ 6 role ต้องยังทำงาน
  3. ตรรกะตายตัวมาก่อน AI เสมอ — ถ้าเขียน if/else ตอบได้ ห้ามเรียกโมเดล
  4. AI ต้องไม่บล็อกทางเดิน — โมเดลล่ม/quota หมด ผู้ใช้ต้องยังทำเองได้ทุกขั้นตามปกติ
  5. มีเพดานค่าใช้จ่ายต่อ org ตั้งแต่วันแรก
  6. ไม่ส่งข้อมูลลูกค้าเข้าโมเดลในฟีเจอร์ชุดนี้ — งานทั้งหมดในแผนนี้เป็นเรื่องตั้งค่าและอุปกรณ์ ไม่ต้องใช้ PII เลย ทำให้ความเสี่ยง PDPA เป็นศูนย์

10. ต้องตัดสินใจก่อนเริ่ม

  1. เริ่มที่ เฟส 1 (onboarding) หรือ เฟส 2 (อุปกรณ์) ก่อน? — อุปกรณ์เจ็บกว่า แต่ onboarding เห็นผลกว้างกว่า
  2. ฟีเจอร์ชุดนี้ ให้ทุกแพ็กเกจใช้ฟรี (เพราะเป้าหมายคือลดคนหลุด) หรือกันบางส่วนไว้ขาย?
  3. เพดานค่าโมเดลต่อร้านต่อเดือนที่รับได้
  4. ทำ pilot ที่ร้านตัวเอง (Each Other, 2 สาขา + เครื่องพิมพ์ PT-280) ก่อนปล่อยจริงหรือไม่
