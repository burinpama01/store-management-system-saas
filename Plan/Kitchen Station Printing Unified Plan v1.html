แผนพิมพ์ตั๋วครัว/บาร์แบบรวม v1

StoreOS · 2026-09-19 · สถานะ: รออนุมัติ · branch ปัจจุบัน feat/table-bill-label

เป้าหมาย: ทุกออเดอร์ที่มีรายการครัว/บาร์ ต้องออกตั๋วที่สถานีของมัน ครั้งเดียวพอดี ไม่ว่าเปิดกี่จอ, ไม่ว่ามาจาก QR / POS จ่ายทันที / ส่งเข้าครัว / เดลิเวอรี — และรองรับ ครัวที่ใช้มือถือ (แอป Android) ต่อเครื่องพิมพ์ Bluetooth ได้ทั้งแบบอยู่วงแลนเดียวกับบาร์และคนละวง

1. สถานการณ์ตั้งต้น (ที่ต้องทำให้ได้)

  • บาร์: พีซี/แท็บเล็ตเปิด POS ค้างไว้ ล็อกอินแคชเชียร์ · เครื่องพิมพ์บาร์ 1 เครื่อง (IP/USB ผ่าน Print Hub)
  • ครัว: แคชเชียร์อีกคนพกมือถือ (แอป Android) · เครื่องพิมพ์ครัว 1 เครื่อง — ต่อ Bluetooth กับมือถือ หรือเป็น IP ในแลนเดียวกับ Hub
  • ครัวอาจอยู่ วงแลนเดียวกัน หรือคนละวง (คนละเราเตอร์/ใช้ 4G) ก็ต้องใช้ได้

2. สภาพปัจจุบัน + ปัญหาที่พบ

ช่องทางตอนนี้ปัญหา
ลูกค้าสั่ง QRจอ dashboard/POS ที่ role ≠ staff แตกตั๋วต่อสถานี → /api/print/enqueue → Hubซ้ำ ทุกจอที่เป็นแคชเชียร์/ผู้จัดการ enqueue ของตัวเอง (enqueue ไม่ส่ง source_key)
POS "ส่งเข้าครัว" (ร้านปกติ)ผ่าน pipeline QR → ได้ตั๋วแบบเดียวกันซ้ำ เหมือนด้านบน
POS "ส่งเข้าครัว" (Unified POS)add_items_to_table_v2 → qr_order_source=false → notifier ไม่เห็นช้า ตั๋วออกตอนเช็คบิล (print-intent)
POS ขาย-จ่ายทันทีautoPrintStationTickets: false (PosTerminal.tsx:4131)ไม่ออก
เดลิเวอรีเข้าprintKitchenForOrder → Hubซ้ำ หลายจอ
มือถือครัว + BLEสวิตช์ "พิมพ์อัตโนมัติ" QR พิมพ์ ทั้งออเดอร์ (รวมรายการบาร์ แบบใบเสร็จ) ผ่าน BLEผิดสถานี + หลับจอ = ไม่พิมพ์ + ไม่ย้อนพิมพ์

หลาย Hub (ครัวคนละแลน มีพีซีของตัวเอง)1 ร้าน = 1 token, claim ทั้งร้านสุ่มหาย Hub ผิดตัวดึงงานไป

⚠️ บั๊กที่น่าจะเกิดอยู่บน prod ตอนนี้ (ขึ้นวันนี้กับ PR#64): RPC consolidate_table_bill INSERT ออเดอร์บิลรวมด้วย qr_order_source=true แล้วย้าย order_items เข้ามาใน transaction เดียว → realtime ส่ง INSERT ให้ QrOrderGlobalNotifier ซึ่งกรองแค่ qr_order_source → เด้งแจ้งเตือน "ออเดอร์ QR ใหม่" + พิมพ์ตั๋วครัวทั้งโต๊ะซ้ำ + auto-print ทุกครั้งที่เช็คบิลรวม. แก้ใน Phase 0 (ยังไม่ได้ทดสอบยืนยันด้วยตา — ต้องลองบน local ก่อน)

3. สถาปัตยกรรมใหม่

3.1 หลักการ

  1. สถานีมี "โหมดพิมพ์" — kitchen_stations.print_mode = hub (เครื่องพิมพ์ผ่าน Hub เหมือนเดิม) | device (มือถือในแอปที่ผูกไว้พิมพ์ BLE) | none
  2. ทุกตั๋วต้อง claim ก่อนพิมพ์ ในตารางใหม่ station_ticket_dispatches unique (order_id, station_id) — ผู้ชนะ claim คนเดียวที่ได้พิมพ์ → จบปัญหาซ้ำทุกช่องทาง/ทุกจอ. เก็บสถานะ claimed → printed | failed สำหรับย้อนพิมพ์ + audit
  3. ยังเรนเดอร์ตั๋วในเบราว์เซอร์ (raster) เหมือนเดิม — ภาษาไทยคมชัด (text ESC/POS ฝั่ง server เคยทำไทยเพี้ยน) ย้ายไป server-side เป็นงานระยะยาว (Phase 5 ทางเลือก)
  4. ตั๋ว 1 ใบ = รายการของ "รอบนั้น" — ทุกรอบสั่ง (QR submit / ส่งเข้าครัว / POS checkout) เป็น orders แถวใหม่อยู่แล้ว จึงใช้ order_id เป็นคีย์ได้. ออเดอร์บิลรวม (table_bill_key ไม่ว่าง) ไม่ออกตั๋วครัวเด็ดขาด
  5. ทุกเส้นทางมี log ลง system_event_logs รวมเส้นทางสำเร็จแบบเงียบ (กฎถาวรของโปรเจกต์)

3.2 ใครเป็นคนสั่งพิมพ์ (dispatcher)

โหมดสถานีใครพยายาม claimเมื่อไหร่
hubทุกจอ dashboard/POS ที่มีสิทธิ์ orders.manage_qr หรือจอ POS ที่สร้างออเดอร์นั้นเอง — แข่งกัน claim, คนแพ้ข้ามทันทีหลังออเดอร์เข้า (realtime) / หลัง action POS สำเร็จ (ไม่ต้องรอ realtime)
deviceเฉพาะมือถือที่ผูกกับสถานีนั้น (localStorage + heartbeat ในตาราง)realtime + ตอนเปิดจอ/เน็ตกลับ (catch-up)

ข้อดี: ไม่ต้องกำหนด "จอหลัก" — จอไหนเปิดอยู่ก็พิมพ์ได้ แต่ออกใบเดียว. ข้อจำกัดที่ยังเหลือ: ถ้า ไม่มีจอไหนเปิดเลย ตั๋ว hub ไม่ออก (แก้จริงคือ Phase 5 server-side)

5. เฟสงาน

Phase 0Hotfix: บิลรวมโต๊ะไม่ออกตั๋วครัว/ไม่เด้งซ้ำ ด่วน web-only · ไม่มี migration
  • ยืนยันบั๊กบน local (dev-local-db): เปิดโต๊ะ → สั่ง QR → ครัวรับ → เช็คบิลรวม → ดูว่า notifier เด้ง/พิมพ์หรือไม่
  • QrOrderGlobalNotifier: ข้าม INSERT ที่ table_bill_key ไม่ว่าง (เพิ่มใน OrderInsertPayload) + เช็คซ้ำตอน fetchVisibleOrder
  • ตรวจ DeliveryGlobalNotifier/บอร์ด QR ว่าไม่นับบิลรวมเป็นออเดอร์ครัวใหม่
  • เทสต์: source-assertion ว่ากรอง table_bill_key + unit test ฟังก์ชันตัดสินใจ
  • ส่งเป็น PR เล็กแยก merge ได้ทันที
Phase 1กันตั๋วซ้ำ (dispatch table + claim) migration
  • migration ตามข้อ 4
  • โมดูลใหม่ src/modules/printing/station-dispatch.ts — dispatchStationTickets({ order, stations, paperWidth }): แตกตั๋ว (reuse buildStationTicketJobs) → ต่อสถานีโหมด hub: claim → render → enqueue พร้อม sourceKey = station:{orderId}:{stationId} → finish
  • /api/print/enqueue: รับ sourceKey (validate รูปแบบ + order เป็นของร้าน) ส่งต่อ enqueuePrintJob ซึ่ง dedupe ด้วย unique index อยู่แล้ว — กันซ้ำชั้นที่สอง
  • เปลี่ยน QR notifier + print-kitchen.ts (เดลิเวอรี) ให้เรียก dispatchStationTickets; เลิกเงื่อนไข "เฉพาะ canViewEveryKitchenStation" (claim กันซ้ำแทน)
  • print-intent.ts (Unified settlement): ข้ามสถานีที่มี dispatch printed ของออเดอร์ต้นทางแล้ว
  • log: station_ticket.claimed / printed / failed / skipped_lost_claim
Phase 2POS ออกตั๋วครัวทุกเส้นทาง web-only
  • POS จ่ายทันที (PosTerminal + GroceryPosTerminal หลัง checkoutAndPayAction สำเร็จ) → dispatchStationTickets — gate ด้วย auto_print_station_tickets (ร้านขายปลีกไม่มีสถานี = ไม่มีผล)
  • "ส่งเข้าครัว" (handleSendToKitchen) → dispatch ทันทีหลัง action สำเร็จ ทั้งร้านปกติและ Unified (v2 path) — ไม่รอ realtime
  • server action คืนรายการพร้อม kitchen_station_id ให้ client (หรือ client ดึงจาก order_items) เพื่อแตกตั๋ว
  • บิลรวมโต๊ะ: รายการที่ค้างในตั๋วโต๊ะแล้วไปสร้างตอนเช็คบิล → ไม่ออกตั๋ว (ดูข้อตัดสินใจ D2)
Phase 3มือถือครัว = เครื่องพิมพ์สถานี (BLE) web-only ส่วนใหญ่
  • ตั้งค่า → ครัว: เลือกโหมดสถานี hub/device/none; dropdown เครื่องพิมพ์ของโหมด hub กรองเฉพาะเครื่องที่ Hub พิมพ์ได้ (ใช้ toHubRoutableTarget/isHubReceiptPrinter)
  • ในแอป (isNativePlatform) หน้าใหม่/การ์ด "เครื่องนี้พิมพ์ตั๋วสถานี: [ครัว]" → เก็บ localStorage + ส่ง heartbeat ทุก 60 วิ (device_label, device_last_seen)
  • มือถือที่ผูกสถานี: รับ realtime orders → claim (channel device) → พิมพ์ตั๋วครัว (ticketMode kitchen, เฉพาะรายการสถานีนั้น) ผ่าน native-print-client → finish
  • Catch-up: ตอน visibilitychange/online/เปิดแอป → station_ticket_backlog ย้อนหลัง 3 ชม. → พิมพ์ที่ยังไม่ printed (ใส่หัว "ตั๋วตกค้าง")
  • จอไม่ดับ: Wake Lock API ในหน้าครัว (WebView รองรับ) + ปุ่มเปิด/ปิด + เตือนถ้าแบต < 20%
  • ปิดสวิตช์ "พิมพ์อัตโนมัติทั้งออเดอร์" เดิมอัตโนมัติเมื่อเครื่องนี้ผูกสถานีแล้ว (กันพิมพ์ทั้งใบซ้อน)
  • หน้าตั้งค่าครัวโชว์ "มือถือครัว: ออนไลน์ 1 นาทีที่แล้ว / ออฟไลน์" + เตือนบนจอบาร์เมื่อสถานี device ออฟไลน์เกิน 2 นาที และมีตั๋วค้าง
  • (ทางเลือก) fallback: ถ้าสถานี device ออฟไลน์ > N นาที ให้ส่งตั๋วไปเครื่องพิมพ์ hub สำรองที่ตั้งไว้

ใช้ได้ทั้งแลนเดียวกันและคนละวง เพราะมือถือคุยกับ cloud ผ่านเน็ตอย่างเดียว ไม่ต้องมี Hub ที่ครัว

Phase 4แอป Android พิมพ์ได้ตอนล็อกจอ ต้องออก APK/AAB ใหม่
  • Android foreground service (แจ้งเตือนถาวร "StoreOS กำลังรับตั๋วครัว") ให้ WebView/realtime ไม่ถูกพัก หรือ native: รับ FCM data message → เปิดแอปมาพิมพ์
  • ตั้งค่าขอยกเว้น battery optimization + คู่มือสำหรับ Xiaomi/OPPO/Vivo ที่ฆ่าแอปพื้นหลัง
  • ต้องอัปเดต Play Store (declaration foreground service type) — ทำหลัง Phase 3 ใช้งานจริงแล้วเห็นว่าจำเป็น
Phase 5ระยะยาว (ทางเลือก)
  • หลาย Hub ต่อร้าน: ตาราง print_hubs (token ต่อ Hub) + printers.hub_id + claim_print_jobs กรองตาม hub — สำหรับครัวคนละแลนที่มีพีซีของตัวเอง
  • Dispatch ฝั่ง server: สร้างตั๋ว hub ทันทีที่ออเดอร์ commit (trigger/after-action) ไม่ต้องมีจอเปิด — ต้องแก้เรนเดอร์ไทยฝั่ง server (raster ด้วย font ใน Node) ก่อน

6. ข้อตัดสินใจที่ต้องการจากผู้ใช้

7. ทดสอบ / ยืนยัน

  • Unit: claim ชนกัน 2 client → พิมพ์ครั้งเดียว; lease หมดแล้ว re-claim ได้; บิลรวมถูกปฏิเสธ
  • Unit: แตกตั๋ว device กรองเฉพาะสถานีของเครื่อง; dropdown กรองเครื่องที่ Hub พิมพ์ได้
  • Integration (local Supabase): RPC claim/finish/backlog + RLS คนนอกร้านอ่านไม่ได้
  • Source-assertion: POS checkout / ส่งเข้าครัว เรียก dispatch; notifier ข้าม table_bill_key
  • Browser (local dev-local-db): เปิด 2 แท็บเป็นแคชเชียร์ → สั่ง QR → print_jobs ได้ 1 แถว/สถานี
  • typecheck + eslint + full suite (ตัด .codex-temp/.worktrees)
  • ฮาร์ดแวร์ที่ร้าน: บาร์ (Hub+IP) + มือถือครัว BLE ทั้งแบบแลนเดียวกันและ 4G; ล็อกจอ 5 นาทีแล้วเปิด → ตั๋วตกค้างออกครบไม่ซ้ำ

8. ความเสี่ยง

  • ไม่มีจอไหนเปิด → ตั๋ว hub ไม่ออก (เหมือนเดิม) — ลดด้วยคำเตือนในตั้งค่า, แก้จริง Phase 5
  • มือถือหลับ/ถูกฆ่าแอป → ตั๋ว device ช้า (catch-up ช่วยได้เมื่อตื่น) — Phase 4
  • BLE หลุดกลางงาน → dispatch = failed → retry อัตโนมัติ 1 ครั้ง + ปุ่ม "พิมพ์ซ้ำ" บนมือถือ
  • Migration ต้องขึ้นก่อนโค้ด — โค้ดต้องทนตารางยังไม่มี (fallback เป็นพฤติกรรมเดิม)
  • Tests ส่วนใหญ่เป็น source-assertion → grep ก่อนแก้ไฟล์ POS
