ข้อเสนอเพิ่มเติมจากแผน AI Onboarding & Device Copilot: แยก “รับเงินแล้วในเครื่อง” ออกจาก “ซิงก์เข้าส่วนกลางแล้ว” พร้อมกู้คืนบิลและป้องกันการรับเงินซ้ำ

สถานะ: เพิ่มแผนตามคำขอแล้ว · ยังไม่เริ่มแก้ระบบ · เงินสดเป็นขอบเขตเริ่มต้นที่เสนอให้อนุมัติ

Goal: POS ปกติที่เปิดและเตรียมพร้อมขณะออนไลน์แล้ว สามารถขายบิลใหม่แบบเงินสดต่อระหว่างเน็ตหลุด และนำ order/payment/stock/cash ledger กลับเข้าส่วนกลางโดยไม่ซ้ำ

Architecture: local journal + outbox ใน IndexedDB, snapshot ที่ server รับรอง, รหัสธุรกรรมเดียวตลอด online/offline/retry, server reconciliation และการยืนยันผลแบบ atomic

Tech Stack: Next.js/React/TypeScript, IndexedDB, Vitest, Supabase/PostgreSQL และ printing adapters เดิม ไม่ใช้ AI ตัดสินยอดเงินหรือสถานะชำระเงิน

สำหรับผู้ลงมือ: ใช้ superpowers:executing-plans หลังผู้ใช้อนุมัติขอบเขต; ทุกงาน payment/security/schema ต้องผ่าน approval และ code_reviewer ก่อนสรุปผล

เลือกขอบเขตให้ตรงคำว่า “เน็ตหลุด”

A · Warm cash checkout

แนะนำเป็นระยะแรก

เปิด POS/เข้าใช้/เปิดกะ/เตรียมข้อมูลขณะออนไลน์ก่อน แล้วขายเงินสดต่อเมื่อเน็ตหลุด ใช้ฐานเดิมได้มากและจำกัดความเสี่ยง

B · เปิดใหม่ออฟไลน์

เพิ่ม dedicated offline shell, asset cache, snapshot และ local unlock สำหรับ reload/cold start หลังเคยเตรียมเครื่องไว้

ต้องมีแผนย่อยและ security review แยก ไม่อ้างว่ามีแล้วเพียงเพราะใช้ IndexedDB

C · Local server ในร้าน

หลายเครื่องใช้ LAN coordinator และ local print spooler แม้ WAN ขาด

ต้องดูแลติดตั้ง/สิทธิ์/อัปเดต/backup เพิ่ม เป็นงานแยก ไม่เปิด public gateway

ขอบเขตเสนอ A: รับเฉพาะเงินสดเต็มยอดสำหรับบิลใหม่แบบ walk-in ไม่มี customer/coupon/reward/credit/split payment และต้องมีกะที่เปิดไว้ก่อน ไม่ครอบคลุมบิลโต๊ะ/บิลค้างที่อาจแก้จากเครื่องอื่น การขยายขอบเขตต้องอนุมัติ ไม่แปลงบิลที่ถูกบล็อกเป็นเงินสดเงียบ ๆ
ทำได้ใน Aต้องรอออนไลน์หรือแผนเพิ่ม
สินค้า/variant/modifier/หน่วยขายที่อยู่ใน snapshot ที่รับรองแล้ว; เงินทอน; ใบรับเงินออฟไลน์ค้นสินค้าที่ไม่เคยโหลด, สร้างสินค้า, เปลี่ยนราคา, ส่วนลดใหม่, เปลี่ยนสาขา/ผู้ใช้, เปิดกะใหม่
ดูยอดเงินสดในเครื่องและบิลรอซิงก์; ลองซิงก์ด้วย operation เดิมคูปอง/แต้ม/สมาชิก/วงเงินเครดิต/คืนเงิน/ยกเลิกบิลที่รับเงินแล้ว และปิดกะส่วนกลางก่อนกระทบยอดครบ
แจ้งว่า QR/โอนต้องรอตรวจสอบห้ามตั้ง qrPaymentVerified หรือ paid จากรูปสลิป/คำบอกเล่า/การกดซ้ำ; external terminal ไม่ได้รองรับ offline authorization โดยอัตโนมัติ

Flow และเงื่อนไขที่ห้ามข้าม

  1. เตรียมเครื่องออนไลน์: server ยืนยัน org/store/user/device, pos.use, offlinePos, กะที่เปิด และออก snapshot/version/ช่วงใช้ได้พร้อม offline allowance
  2. ก่อนรับเงิน: ตรวจ scope, snapshot ยังใช้ได้, พื้นที่เก็บและ queue limit; freeze cart/ยอดเป็นหน่วยสตางค์ สร้าง saleId/orderKey/paymentKey เพียงครั้งเดียว แล้วบันทึก prepared journal
  3. แคชเชียร์รับเงิน: ใส่เงินที่รับและยืนยันได้รับเงินจริง; เขียน payment evidence + outbox ใน transaction เดียว รอ transaction complete ก่อนล้าง cart/พิมพ์/ขึ้นข้อความสำเร็จ
  4. เน็ตหลุดกลาง request: เก็บสถานะ unknown; ห้ามสร้าง sale ใหม่หรือรับเงินอีก ส่งซ้ำหรือ query ผลด้วยรหัสเดิมเมื่อกลับมา การ offline fallback ต้องอ้าง sale เดิมที่บันทึกก่อน request
  5. เน็ตกลับ: online event เป็นเพียงสัญญาณ → ตรวจ endpoint จริง → re-auth หากจำเป็น → replay แบบ single writer พร้อม backoff/jitter และ bounded timeout
  6. server รับ: ตรวจ identity และ signed snapshot/allowance → dedup โดย immutable payload hash → ยืนยัน order/payment/stock/cash journal + mapping ผลสำเร็จ atomically หรือเข้าคิว reconcile ที่ตรวจสอบย้อนหลังได้
  7. ยืนยันกลับเครื่อง: บันทึก server IDs/receipt mapping จน transaction complete จึงนับซิงก์ครบ; ไม่ลบ unsynced operations ด้วยอายุ/clear cache/การอัปเดตแอป
ถ้ารับเงินสดจริงแล้วแต่บันทึกเครื่องล้มเหลว ต้องแสดง “รับเงินแล้วแต่บันทึกไม่สำเร็จ — ห้ามรับเงินซ้ำ” คง cart และ saleId, ให้จดหลักฐานฉุกเฉิน/หยุดรับบิลใหม่ ไม่แสดงว่าเงินยังไม่ถูกจ่ายและไม่ส่งบิลใหม่โดยอัตโนมัติ หากแอปดับระหว่างยืนยัน เงินสดจริงต้องให้แคชเชียร์ตรวจ prepared journal ก่อนดำเนินต่อ
สถานะความหมาย / สิ่งที่ทำต่อได้
preparedสร้าง intent แล้ว แต่ยังไม่ถือว่าได้รับเงิน; กู้คืนให้แคชเชียร์ตรวจว่ารับเงินจริงหรือยัง
cash_recorded / pending_syncรับเงินแล้วในเครื่อง; พิมพ์หลักฐานได้; ห้ามรับเงินอีกหรือแก้ยอดทับ
syncing / unknownอาจมี commit บน server แล้ว; retry ด้วย IDs เดิม ไม่เปลี่ยน payment status เป็น unpaid
syncedserver ยืนยันผลและ local mapping บันทึกแล้ว; พิมพ์ซ้ำเป็น “สำเนา”
needs_review / auth_requiredเงินยังถือว่ารับแล้ว แต่ accounting ยังไม่ reconcile; แสดงเหตุผลและผู้รับผิดชอบ ไม่ retry 409/403 วนไม่สิ้นสุด

  • จำนวนเงินเป็น integer สตางค์; quantity มี scale ชัดเจน ใช้กติกาปัดเศษเดียวกับ server ไม่ใช้ floating-point รวมยอดสองวิธี
  • saleId เป็น UUID ที่ไม่พึ่งเวลาล้วน; localReceiptRef เป็นเลขอ้างอิงเครื่อง ไม่สวมเป็นเลขใบเสร็จ server; เวลาเครื่องใช้แสดงเหตุการณ์ ไม่ใช่หลักฐานอนุญาตสิทธิ์
  • server เก็บ snapshot/allowance เพื่อพิสูจน์ราคาที่อนุญาตขาย ไม่เชื่อ client total หรือ signature ที่ client สร้างเอง; snapshot หมดอายุ/ถูกดัดแปลงต้องเข้าสู่ review
  • ยอดบิลที่รับเงินจริงแล้วต้องไม่ silent reprice ตอน sync; การแก้ต้องเป็น adjustment ที่มีเหตุผล/ผู้อนุมัติ/ประวัติเดิม ไม่ overwrite เงินที่รับ
  • server dedup scope org+store+saleId; orderKey และ paymentKey คงเดิมทุก retry; key เดิม payload ต่าง = conflict ไม่คืนสำเร็จหรือสร้างใหม่
  • ห้ามเก็บ password, access/refresh token, service key, รูปสลิป หรือ PII สมาชิกเพิ่มใน offline journal; device local storage ไม่ใช่ secure vault โดยตัวมันเอง

Approval และสิ่งที่ยังไม่รับรอง

  • คำขอครั้งนี้อนุมัติให้เพิ่มแผน ไม่ใช่อนุมัติแก้ payment/auth/data หรือ production
  • รอยืนยัน A เงินสด/warm offline, outage limits และ stock/cash reconciliation policy ก่อน implementation; B/C ทำแยกตามความจำเป็น
  • feature flag เริ่มปิด; rollback ปิด new offline sale แต่ไม่ลบ queue/schema และไม่ปิด recovery ของเงินที่รับแล้ว
  • ไม่แก้ entitlement ของแพ็กเกจโดยปริยาย ไม่กำหนดว่า offline ฟรีทุกแผน และไม่ใช้สิทธิ์ client แทน server
  • ไม่รับรอง browser storage ทนการล้างข้อมูล/เครื่องเสีย/ไฟดับทุกกรณี; persistence เป็นการลดความเสี่ยง ไม่ใช่ backup สำรองแยกเครื่อง

เอกสารอ้างอิงที่ตรวจ

  • MDN: transaction complete — ยืนยัน commit ก่อนแจ้งสำเร็จ
  • MDN: storage quotas / eviction — ต้องมี storage-failure และ recovery policy
  • MDN: navigator.onLine — เป็นสัญญาณ ไม่ใช่หลักฐานเข้าถึง backend

ตรวจเอกสาร: scope/flow/contracts/tasks/acceptance ครบสำหรับข้อเสนอเพิ่มเติมนี้; ยังไม่มี runtime implementation, automated feature tests, DB migration หรือ real-device validation ในรอบจัดทำแผน
