3. รีวิว Voice Standby v1

3.1 สิ่งที่ทำได้ดี (ควรคงไว้ทุกข้อ)

  • เลือกสถาปัตยกรรม B (WPF + WebView2) ถูก — ทางเลือก A (browser continuous) พังเรื่อง permission/background/tab จริง ส่วน C (localhost agent) เพิ่ม CORS/PNA/replay attack surface แลกกับความสะดวกเท่านั้น การเขียนเหตุผลปฏิเสธ A/C ไว้ในเอกสารทำให้คนอ่านทีหลังไม่รื้อการตัดสินใจซ้ำ
  • origin-aware policy คือหัวใจ — แยก push_to_talk กับ windows_standby แล้วบังคับว่า Tier B (แก้ตะกร้า) ต้อง preview + ยืนยันภายใน 8 วินาที ถ้าไม่มีข้อนี้ false wake ครั้งเดียวคือตะกร้าเพี้ยนเงียบ ๆ กลางชั่วโมงเร่ง
  • re-resolve snapshot ก่อน commit (W6) — กันเคส proposal ค้าง 8 วิแล้วตะกร้าเปลี่ยนไปแล้ว เป็นรายละเอียดที่แผนทั่วไปมักลืม
  • privacy contract วัดผลได้ — ring buffer ≤2 วินาที, ห้าม transcript ลง log, และ canary test (ยัด transcript/เบอร์/token ปลอมแล้ว assert ว่าไม่โผล่ใน log/bundle) เป็นวิธีพิสูจน์จริง ไม่ใช่แค่สัญญาในเอกสาร
  • fail-closed ทุกทาง — unknown/low confidence = no-op; mic denied / WebView2 หาย = degraded ไป push-to-talk โดยไม่ crash
  • ห้าม synthetic click เพื่อข้าม user-activation — สำคัญมาก เพราะเป็นทางลัดที่มักถูกเลือกแล้วทำให้ทั้งฟีเจอร์กลายเป็นของเปราะที่พังทุกครั้งที่เบราว์เซอร์อัปเดต

3.2 ปัญหาที่ต้องแก้

CRITICAL F1 — mic ownership contract ใช้กับโค้ดปัจจุบันไม่ได้

แผนสมมติว่าเว็บเป็น one-shot ล้วน: native stop → wake.detected → web one-shot → command.ended → cooldown 350ms → standby resume

แต่ commit หลังแผน (814420b, 73bbd8c) เปลี่ยนพฤติกรรมเป็น สายการฟังต่อเนื่อง: หลังระบบบอกว่า "ยังต้องเลือกอะไร" จะเปิดไมค์รอบใหม่เอง และยืดเวลารับเสียงเป็น 15 วินาที (VoiceCommandButton.tsx:265)

ผลกระทบ: native จะเข้าใจว่า command จบตั้งแต่ utterance แรก แล้ว resume standby ทับตอนที่เว็บยังถือไมค์อยู่ → device busy / session ซ้อน ซึ่งทำให้ success criteria ข้อ "500 รอบ handoff ไม่มี device busy" fail แน่นอน

แก้: นิยาม command.ended ใหม่ให้หมายถึง "จบทั้งสายฟัง" (รวมรอบถามตัวเลือกต่อเนื่อง) + เพิ่ม heartbeat หรือ command.extended เพื่อกัน watchdog ตัดกลางสาย + ปรับ watchdog จาก 15s เป็น ≥20s ให้ยาวกว่าเวลารับเสียงฝั่งเว็บเสมอ

HIGH F2 — wake engine เป็น en-US บนเครื่องที่ใช้งานภาษาไทย

W2 กำหนด Culture = en-US, threshold 0.82 ผ่าน System.Speech constrained grammar ขณะที่คำสั่งจริงเป็น th-TH ผ่าน Web Speech ปัญหาคือเครื่อง Windows ที่ขายในไทยจำนวนมากไม่มี recognizer en-US ติดตั้ง และ System.Speech ไม่มี th-TH ให้ใช้เลย

แผนรู้ข้อนี้และวาง STOP gate ไว้ที่ W0 ซึ่งถูกต้อง แต่โครงสร้างการอนุมัติกลับเสนอ W0–W12 มาเป็นก้อนเดียว

แก้: แยก W0 เป็นการอนุมัติต่างหาก (spike ~1 วัน) พร้อมเกณฑ์ตัดสินชัดเจน — ถ้า reference hardware ไม่มี en-US recognizer หรือ recall ต่ำกว่าเป้า ให้ประเมิน engine ทางเลือก (คนละ licensing model) ก่อน ลงทุน W1–W12

HIGH F3 — ต้นทุนไม่สมมูลกับปัญหาที่ร้านเจออยู่จริง

W0–W12 + MSIX + code signing + burn-in 72 ชม. + pilot 21 วัน = งานหลายสัปดาห์ บวกค่าใบรับรองและภาระ support ระยะยาว (ตามอัปเดต WebView2, ไดรเวอร์เสียง, Windows policy)

ขณะที่งานค้างที่กระทบร้านตรง ๆ ตอนนี้คือ ใบเสร็จ USB ที่ยังไม่ deploy และ Print Hub ที่ยังไม่มี health/mutex/สถานะงานที่เชื่อถือได้

แผนไม่มีหัวข้อ "ทำไมไม่ทำ" หรือประมาณการว่าปุ่มกดพูดที่มีอยู่แล้วแก้ปัญหาไปได้กี่เปอร์เซ็นต์ — wake word แก้เฉพาะกรณี "มือไม่ว่าง/มือเปียก" ซึ่งควรมีตัวเลขรองรับก่อนลงทุน

แก้: เพิ่ม business case สั้น ๆ (ความถี่ที่พนักงานกดปุ่มไม่ได้ต่อกะ จากร้านนำร่อง 3 ร้านที่เปิด voice อยู่แล้ว) และจัดลำดับให้ Print Hub มาก่อน

MEDIUM F4 — version train 12 bump ต่อ 12 work package

0.42.0 → 0.42.11 ทั้งหมดอยู่ก่อน pilot ทำให้ release history เต็มไปด้วยเวอร์ชันที่ไม่มีใครใช้ และการ rollback อ่านยาก

แก้: bump ที่ milestone จริง 4 จุดพอ — host skeleton / standby policy / RC / pilot

MEDIUM F5 — ยังไม่มีคำตอบเรื่องการออกเสียงคำปลุกโดยผู้พูดไทย

แผนตัด Thai wake word ออกจาก v1 อย่างถูกต้อง แต่พนักงานที่พูดไทยทั้งวันจะออกเสียง "Hey StoreOS" ไม่สม่ำเสมอ ซึ่งกระทบ recall โดยตรง ส่วน negative corpus ที่วางไว้ (เพลง/ทีวี/บทสนทนา/เสียงเครื่องชง) ยังไม่ครอบคลุมกรณี "พนักงานพูดไทยปนอังกฤษกันเอง"

แก้: ระบุใน G6 ว่า positive corpus ต้องมาจากผู้พูดไทย ไม่ใช่ native speaker และ negative corpus ต้องมีบทสนทนาไทยในร้าน

LOW F6 — ไม่มี logging ฝั่งเซิร์ฟเวอร์ตามกฎโปรเจกต์

AGENTS.md กำหนดว่าทุกฟีเจอร์ใหม่ต้องเขียน system_event_logs รวมถึงเส้นทางที่สำเร็จ แผนพูดถึง diagnostics ฝั่ง native (local, privacy-safe) แต่ไม่มีการบันทึกฝั่งเซิร์ฟเวอร์เลย — เช่นจำนวน standby activation ต่อร้าน, จำนวน confirm/cancel/timeout ซึ่งเป็นตัวชี้วัดเดียวที่จะบอกได้ว่าฟีเจอร์นี้ถูกใช้จริงไหมหลัง pilot (นับ event แบบไม่มี transcript ไม่ขัดกับ privacy contract)

4. รีวิว Voice Standby + Print Hub v2

4.1 สิ่งที่ทำได้ดี

  • "StoreOS default ≠ Windows system default" — ตัดสินใจถูกและควรบันทึกเป็น ADR จริง เพราะการแก้ Windows default printer คือการเปลี่ยนสภาพเครื่องของลูกค้าโดยที่ระบบเราไม่มีสิทธิ์
  • Priority P1–P5 + กฎห้ามเดา — โดยเฉพาะ "ห้ามใช้ display name เป็น stable identity" และ "ห้ามเปลี่ยน binding ที่เคยยืนยันเพราะมีเครื่องอื่นถูกเสียบทีหลัง"
  • งานสถานะ unknown ห้าม auto-replay — ตรงกับบทเรียนจริงของโปรเจกต์นี้ที่เคยมีปัญหาใบเสร็จซ้ำจนต้องทำ localStorage claim กันปริ้นซ้ำข้ามแท็บ
  • kill switch แยก 4 ตัว พร้อมเงื่อนไข "ปิด autostart ต้องไม่ลบ binding / ปิด discovery ต้องยังเลือกด้วยมือได้" — ออกแบบ degradation ถูกหลัก
  • launch lease + ห้ามคงสองกลไก autostart — ตรงกับความเสี่ยงจริงที่มี Scheduled Task StoreOSPrintHub อยู่แล้ว
  • ไม่รวม process กับ Print Hub และไม่ reuse hubToken — การแยก credential ระหว่างสองระบบเป็นการตัดสินใจที่ถูก

4.2 ความขัดแย้งกับโค้ดที่ ship ไปแล้ว

แผน USB Auto Detect ถูก implement แล้ว (b6b80c2, migration 20260904000003_print_hub_usb.sql) ตารางนี้คือจุดที่ v2 ขัดกับของจริง

หัวข้อv2 กำหนดว่าโค้ดที่รันอยู่ผล
ที่เก็บ binding local-first: JSON config ใน Print Hub (schemaVersion, atomic write, backup) server-first: printers.hub_usb_name ใน Supabase + ผลสแกนเข้า stores.print_hub_devices ขัดกัน ทำทั้งสองอย่าง = source of truth สองที่
Device identity stable device id / VID+PID+serial; ห้ามใช้ display name เป็น key ใช้ชื่อเครื่องพิมพ์ของ Windows เป็น key ตรง ๆ ขัดกัน
Auto-selection "เลือกจากชื่อคล้ายกันแบบเดา" อยู่ใน Non-goals pickUsbPrinter() จัดอันดับด้วย regex ชื่อ POS/Thermal/Receipt/58/80/XP-/TM-/EPSON/RP/PT- ขัดกัน
Windows default printer ไม่อ่าน ไม่เปลี่ยน tier 4 ของ pickUsbPrinter() = fallback ไปเครื่องพิมพ์ default ของ Windows เสี่ยงจริง ใบเสร็จอาจไหลไปเครื่องพิมพ์ A4/PDF ของสำนักงาน
เครื่องใหม่ 1 เครื่อง P4 = เสนอเท่านั้น ต้อง test print + ยืนยันก่อน save binding auto-bind และพิมพ์ได้ทันทีโดยไม่ต้องยืนยัน ขัดกัน แต่เป็นสิ่งที่ทำให้ UX "เสียบแล้วใช้ได้เลย" ตามโจทย์เดิม
Role receipt/kitchen/label เพิ่ม role binding ระดับเครื่องใน Hub มี src/modules/printing/station-routing.ts ผูกเครื่องพิมพ์ต่อ kitchen station ในฐานข้อมูลอยู่แล้ว (ship 2026-06-27) ซ้ำซ้อน จะมีสองระบบตัดสินว่าใบไหนไปเครื่องไหน

ข้อเสนอ reconcile สำหรับ v3: คงสถาปัตยกรรม server-first ที่ ship แล้ว เพราะแท็บเล็ต/iPad ต้องอ่าน binding เดียวกันผ่านคิว (WebUSB/BLE ใช้ไม่ได้บน iOS อยู่แล้ว) แล้วยกของดีจาก v2 มาทับ 4 อย่าง:

  1. เพิ่ม stable identity (VID/PID + serial + PnP device id) เป็นฟิลด์เสริมข้าง hub_usb_name และใช้ match ก่อนชื่อเสมอ
  2. ถอด tier-4 Windows-default ออกจากการเลือกอัตโนมัติ หรือเปลี่ยนเป็น "เสนอให้ยืนยัน" แทนการพิมพ์ทันที
  3. confirm-before-bind เป็นตัวเลือกของร้าน (เปิดเมื่อมีเครื่องพิมพ์หลายตัว) โดยคง auto-detect เป็น default สำหรับร้านเครื่องเดียว
  4. ให้ role/station ใช้ตารางเดิม (kitchen_stations → printer) ไม่สร้าง role binding ชั้นที่สองใน Hub

4.3 ช่องว่างอื่นของ v2

  • W0 สมมติว่ามี health endpoint/IPC ให้ probe — ไม่มีจริง print-hub.mjs เป็น long-poll client ล้วน ไม่เปิด socket ใด ๆ และไม่มี single-instance guard ดังนั้น lifecycle ข้อ 1–3 (Probe 1.5s → Start → Ready 10s) ต้องเริ่มจากการสร้างทั้ง health และ mutex ก่อน ไม่ใช่ "ตรวจของเดิม" ข้อนี้เปลี่ยนขนาดงาน W2/W3 อย่างมีนัยสำคัญ
  • ไม่มีการรับมือ Hub เวอร์ชันเก่า agent ไม่ส่ง version ในการ poll เซิร์ฟเวอร์จึงไม่รู้ว่าร้านไหนรันตัวเก่า — ปัจจุบัน agent เก่าที่ได้งาน kind:"usb" จะตกเข้า branch IP แล้ว ack กลับว่า "Invalid or disallowed IP address" ซึ่งผู้ใช้ตีความไม่ออก
  • "Launcher v1 plan" ที่อ้างถึงไม่มีอยู่จริง ต้องระบุให้ชัดว่า Launcher คือ process เดียวกับ VoiceHost (WPF ตัวเดียวคุมทั้งไมค์และ Hub) หรือคนละตัว ข้อนี้เปลี่ยน scope ทั้ง W2 และ W8
  • Uninstall/upgrade ปะทะ Scheduled Task เดิม v2 ให้เลือกเจ้าของ autostart หลัง pilot แต่ไม่ได้ระบุพฤติกรรมของ uninstall-windows.ps1 ที่มีอยู่ ซึ่งจะลบ task ทิ้ง ถ้า Launcher เป็นเจ้าของแล้วผู้ใช้รัน uninstall เดิม จะเกิดสภาพ "ไม่มีใครเปิด Hub" โดยไม่มีใครรู้
  • ไม่มี logging ฝั่งเซิร์ฟเวอร์เช่นกัน — การเปลี่ยน binding, การพบ/หายของอุปกรณ์ และการ auto-select ควรลง system_event_logs ตามกฎโปรเจกต์ (ปัจจุบันมีแค่ผลพิมพ์ที่ api/print/hub/ack)

5. ปัญหาข้ามแผน (ทั้งสองฉบับไม่ครอบคลุม)

CRITICAL X1 — คิวงานพิมพ์ไม่มีสถานะ unknown และไม่มีการกู้งานค้าง

v2 พูดถึง queued/sent/acknowledged/unknown อย่างถูกต้อง แต่ของจริงคือ:

status check (status in ('pending','claimed','printed','failed'))   -- 20260625120000
attempts integer not null default 0    -- ไม่เคยถูก +1 ที่ไหนเลย
claimed_at timestamptz                 -- ไม่มีโค้ดไหนอ่านกลับ

ผลกระทบจริง: ถ้า Hub เคลมงานแล้วเน็ตหลุด/เครื่องดับก่อน ack งานจะค้างสถานะ claimed ตลอดไป ไม่มี requeue ไม่มี timeout และหน้า Settings ก็มองไม่เห็น เพราะตัวนับแสดงเฉพาะ pending ผู้ใช้จะเจอ "ใบเสร็จไม่ออก แต่ระบบไม่ฟ้องอะไรเลย" ซึ่งเป็นเคสที่หาสาเหตุยากที่สุดหน้าร้าน และตรงกับกฎ "ห้ามสำเร็จแบบเงียบ" ของโปรเจกต์

แก้ (ควรทำก่อนงานใหญ่ทั้งสองแผน): เพิ่มสถานะ unknown + คืนงานที่ค้าง claimed เกิน N นาทีกลับคิวโดยไม่ auto-reprint (ให้ผู้ใช้ตัดสินใจ) + นับ attempts จริง + แสดงงานค้างในหน้า Settings พร้อมปุ่มสั่งพิมพ์ซ้ำด้วยมือ

HIGH X2 — สองแผนอธิบายความสัมพันธ์ของ process ไม่ตรงกัน

v1 ระบุว่า "ไม่รวม process กับ Print Hub หรือ reuse hubToken" ส่วน v2 ให้ Launcher เป็นผู้ดูแล Print Hub สภาพหลังทำครบทั้งสองแผนจะมี Scheduled Task + Launcher (WPF) + WebView2 + เบราว์เซอร์ที่พนักงานอาจเปิดคู่กัน บนเครื่องแคชเชียร์เครื่องเดียว

แก้: freeze process model ให้จบก่อนเขียนโค้ดบรรทัดแรก — ผมแนะนำ WPF ตัวเดียวเป็นเจ้าของ lifecycle ของ Hub (supervisor) แต่แยก credential/config กันสนิทตามที่ v1 กำหนด

MEDIUM X3 — ไม่มีแผนถอนตัวระดับผลิตภัณฑ์

ทั้งสองแผนมี rollback ทางเทคนิคครบ แต่ไม่มีเกณฑ์ว่า "ถ้า pilot ผ่านแต่ร้านไม่ใช้ จะเลิกเมื่อไหร่" ซึ่งสำคัญ เพราะ Windows host ที่ปล่อยไปแล้วกลายเป็นภาระ support ถาวร (ตามอัปเดต WebView2 / ต่ออายุใบรับรอง / Windows policy) แม้ไม่มีใครใช้

MEDIUM X4 — อุปกรณ์ที่ไม่ใช่ Windows ยังไม่อยู่ในสมการ

ร้านจริงใช้ iPad และแอปมือถือปล่อยแค่ Android ทุกอย่างที่ผูกกับ Windows host จะใช้ไม่ได้บนอุปกรณ์เหล่านั้น แผนควรระบุเป็นข้อกำหนดว่า standby เป็นฟีเจอร์เฉพาะเครื่อง Windows และ UI ของอุปกรณ์อื่นต้องไม่แสดงตัวเลือกนี้เลย (v1 ครอบคลุมโดยบังเอิญผ่านข้อ "browser ปกติไม่เห็น toggle")

6. ลำดับงานที่เสนอ

ลำดับงานทำไมต้องมาก่อนขนาด
1ปิดงาน USB ที่ค้าง: apply migration → deploy → ทดสอบกระดาษจริง + log การสแกน + ส่ง agent versionโค้ดอยู่ใน main แล้วแต่ยังไม่ถึงมือร้าน การปล่อยค้างคือความเสี่ยงสะสมเล็ก
2X1 คิวงานพิมพ์: สถานะ unknown + คืนงานค้าง + นับ attempts + แสดงในหน้า Settingsเป็นบั๊กเงียบที่กระทบทุกช่องทางพิมพ์ตอนนี้ ไม่ใช่ฟีเจอร์ใหม่เล็ก–กลาง
3v3 Print Hub reconcile: stable identity + ถอด Windows-default fallback + confirm-before-bind + mutex/health/version ใน agentยกของดีจาก v2 มาทับของที่ ship แล้ว โดยไม่สร้าง source of truth ที่สองกลาง
4Launcher/supervisor (ถ้ายังต้องการ) — ตัดสินใจเจ้าของ autostart ทางเดียวเป็นเจ้าของ process ของทั้ง Hub และ VoiceHost จึงต้องมาก่อน voiceกลาง
5Voice Standby W0 spike เท่านั้น: probe recognizer + mic handoff 100 รอบ + WebView2 postMessage สองทางพิสูจน์สมมติฐานที่ทำให้ทั้งแผนล้มได้ ด้วยต้นทุน 1 วันเล็ก
6ตัดสินใจเดินต่อ/หยุด Voice Standby จากผล W0 + business caseอย่าลงทุน 12 work package ก่อนรู้ว่า engine ใช้ได้จริง—

7. Gate ที่ควรคง / ควรปรับ

Gateความเห็น
G3 Safety (standby Tier B confirm 100%, forbidden execute = 0)คงไว้ เป็น gate ที่มีค่าที่สุดของทั้งแผน
G5 Privacy (canary + network/file scan)คงไว้ วัดผลได้จริง
G4 OS isolation (Windows default ไม่เปลี่ยน)คงไว้ และต้องขยายให้ครอบคลุมโค้ดที่ ship แล้ว ซึ่งอ่านค่า default อยู่
G7 Reliability burn-in 72 ชม.ปรับ ใช้ 24 ชม. ก่อน pilot แล้วค่อย 72 ชม. ก่อน production เพื่อไม่ยืดรอบ feedback
G9 Pilot 21 วัน (1→3 เครื่อง)คงไว้ สมเหตุสมผลกับความเสี่ยงเรื่องตะกร้า
version train 12 bumpตัด เหลือ 4 milestone

8. สรุป

ทั้งสองแผนเขียนดีกว่ามาตรฐานทั่วไปมาก — มี decision record, gate ที่พิสูจน์ได้, non-goals ที่ชัดเจน และ fail-closed ทุกทาง ปัญหาไม่ได้อยู่ที่คุณภาพการเขียน แต่อยู่ที่ ความสดของ baseline (โค้ดขยับหลังแผนภายในไม่กี่ชั่วโมง) และ ลำดับการลงทุน (แผนใหญ่สองฉบับถูกวางทับงานพื้นฐานของ Print Hub ที่ยังไม่เสร็จ)

คำแนะนำสุดท้าย: อย่า implement v2 ตามตัวอักษร ให้ออก v3 ที่ reconcile กับสิ่งที่ ship แล้ว, ปิดหนี้เทคนิคของคิวงานพิมพ์ (X1) ก่อน, และอนุมัติ Voice Standby แค่ W0 จนกว่าจะมีหลักฐานเรื่อง recognizer
