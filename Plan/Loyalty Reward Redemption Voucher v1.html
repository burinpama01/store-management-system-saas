ปรับปรุงหน้าแลกแต้มของลูกค้า — ระบบโค้ดแลกรับ (Reward Voucher)

เวอร์ชัน v1 · 2026-06-25 · สถานะ: รออนุมัติก่อนลงมือ

1. เป้าหมาย (จากคำขอ + คำตอบเจ้าของร้าน)

  • กดแลกแล้วได้ "โค้ดแลกรับ" ที่นำไปกรอกในช่องคูปองที่ POS ได้เลย — เจ้าของร้านเลือกได้ว่าให้ระบบสร้างโค้ดอัตโนมัติ หรือกำหนดโค้ดเอง
  • ของรางวัลแบบส่วนลด (เช่น 10 แต้ม = ลด 10 บาท) → ตอนแลก ระบบ ออกคูปองส่วนลดอัตโนมัติ ใช้กับช่องคูปอง POS เดิม
  • ของรางวัลแบบสินค้า (เช่น 50 แต้ม = หมวก, 100 แต้ม = แก้วน้ำ) → ตอนแลกได้โค้ด พนักงานกรอกโค้ดที่ POS เพื่อ เพิ่มสินค้าเป็นรายการบนใบเสร็จ
  • เพิ่มรูปภาพ ให้แต่ละรายการของรางวัล
  • ประวัติแลก กดดูรายละเอียดได้ + แท็บ "รายการแลกของรางวัล" เก็บประวัติทั้งหมดในหน้า member portal

กติกาของโค้ด (ยืนยันแล้ว)

  • คูปอง/โค้ดมีอายุ 30 วัน นับจากวันแลก
  • ใช้ได้ครั้งเดียวเท่านั้น — เมื่อใช้แล้วตัดทันที
  • แต้มถูกหักทันทีตอนกดแลก (เหมือนเดิม)

2. แนวคิดออกแบบ

ใช้ของเดิมให้มากที่สุด: ตาราง coupons + ระบบ evaluate คูปองที่ POS รองรับ single-use / หมดอายุ / ผูกลูกค้า อยู่แล้ว ดังนั้น reward แบบส่วนลด = สร้าง row คูปองจริง → ไม่ต้องแก้โค้ด POS เลย

ส่วน reward แบบสินค้า ต้องมี path ใหม่ที่ POS (เติมรายการลงตะกร้า) จึงแยกเป็น Phase 2

ประเภท rewardตอนกดแลกตอนใช้ที่ POS
ส่วนลด (discount) หักแต้ม + สร้าง row ใน coupons (single-use, 30 วัน, ส่วนลดตาม reward) + บันทึก voucher กรอกโค้ดในช่องคูปองเดิม → ระบบหักส่วนลดอัตโนมัติ (ใช้ flow เดิม)
สินค้า (product) หักแต้ม + สร้าง voucher (โค้ด + อายุ 30 วัน) — ไม่สร้างคูปองส่วนลด กรอกโค้ดในช่องเดิม → ระบบเติมสินค้าของรางวัลเป็นรายการราคา 0 บนบิล + ตัด voucher

3. การเปลี่ยนโครงสร้างฐานข้อมูล migration ใหม่

3.1 ตาราง loyalty_rewards — เพิ่มคอลัมน์

คอลัมน์ชนิดความหมาย
reward_typetext check('discount','product') default 'product'ประเภทของรางวัล
discount_kindtext check('amount','percentage') nullสำหรับแบบส่วนลด: บาท/เปอร์เซ็นต์
discount_valuenumeric(12,2) nullมูลค่าส่วนลด
reward_product_iduuid null → products(id)(ทางเลือก) ผูกสินค้าจริงสำหรับแบบสินค้า เพื่อเติมรายการที่ POS
image_urltext nullรูปของรางวัล
code_modetext check('auto','manual') default 'auto'สร้างโค้ดอัตโนมัติ หรือกำหนดเอง
manual_codetext nullโค้ดที่เจ้าของกำหนด (เมื่อ code_mode='manual')

3.2 ตาราง loyalty_reward_redemptions — เพิ่มคอลัมน์ (เก็บ voucher)

คอลัมน์ชนิดความหมาย
voucher_codetext — unique(store_id, voucher_code)โค้ดที่ลูกค้านำไปกรอก
coupon_iduuid null → coupons(id)สำหรับ reward ส่วนลด: คูปองที่ออกให้
expires_attimestamptzวันหมดอายุ (แลก + 30 วัน)
used_attimestamptz nullเวลาที่ใช้โค้ด
used_order_iduuid null → orders(id)บิลที่ใช้โค้ด

สถานะใช้คอลัมน์ status เดิม: pending=ใช้ได้ · fulfilled=ใช้แล้ว · cancelled=ยกเลิก/หมดอายุ

3.3 RPC redeem_loyalty_reward — ปรับให้ออก voucher/คูปองแบบ atomic

  • หลังหักแต้ม + ลด stock เดิม → คำนวณ voucher_code (auto = สุ่ม 6–8 ตัว ตรวจชนกัน / manual = ใช้ manual_code)
  • ถ้า reward_type='discount' → insert row coupons (code=voucher_code, discount จาก reward, max_redemptions=1, ends_at=now+30d) แล้วเก็บ coupon_id
  • set expires_at = now() + interval '30 days' ใน redemption
  • คืน voucher_code + ประเภท เพื่อแสดงผลฝั่งลูกค้า

3.4 RPC ใหม่ consume_reward_product_voucher (Phase 2)

ตรวจ voucher แบบสินค้า (ยังไม่ใช้ + ไม่หมดอายุ) แล้ว mark used + ผูก order — เรียกตอนปิดบิลที่ POS

5. ตัวอย่าง flow ฝั่งลูกค้า

[member portal] กด "แลก" หมวก (50 แต้ม) → หักแต้ม 50, สร้าง voucher code "GIFT-7K2P9" (อายุ 30 วัน) → จอแสดง: ✅ แลกสำเร็จ โค้ดแลกรับ: GIFT-7K2P9 นำโค้ดนี้ให้พนักงานที่ร้าน · ใช้ได้ถึง 25 ก.ค. 2026 → แท็บ "รายการแลกของรางวัล": หมวก · GIFT-7K2P9 · รอใช้ · กดดูรายละเอียด [POS] พนักงานกรอก "GIFT-7K2P9" ในช่องคูปอง → (ส่วนลด) หักเงินอัตโนมัติ / (สินค้า) เพิ่ม "🎁 หมวก ฿0" ลงบิล → ปิดบิล → voucher = ใช้แล้ว (ตัด single-use)

6. คำถาม/ข้อกำหนดที่ตั้งเป็นค่าเริ่มต้นไว้ (ทักท้วงได้)

  • รูปแบบโค้ด auto: ตัวอักษร+ตัวเลข 6–8 หลัก (เลี่ยงตัวสับสน 0/O/1/I) เช่น R7K2P9
  • โค้ด manual: ถ้าเจ้าของกำหนดเอง ระบบต่อท้ายเลขลำดับสั้นๆ เพื่อให้ unique ต่อการแลก (กัน single-use ชนกัน) — หรือถ้าต้องการโค้ดตายตัวตัวเดียว แจ้งได้
  • reward แบบสินค้า + ผูกสินค้าจริง: ใช้ reward_product_id เพื่อเติมรายการที่ POS อัตโนมัติ ถ้าไม่ผูก = พนักงานเพิ่มรายการเอง โดยโค้ดเป็นเพียงหลักฐาน
  • Bucket รูป: ใช้ product-images เดิม (อัปโหลดฝั่งหลังร้าน/manager, ลูกค้าอ่าน public)
  • ฟีเจอร์ gating: ยังอยู่ใต้ loyaltyPoints (Enterprise) เหมือนเดิม
