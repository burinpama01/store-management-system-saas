ตัวเลือกขอบเขต

A. Offline Shell

เร็วและเสี่ยงต่ำ เหมาะสำหรับให้แอปเปิดได้ตอนเน็ตหลุด แต่ยังไม่รับ transaction offline.

  • เพิ่ม manifest.webmanifest
  • เพิ่ม service worker cache เฉพาะ app shell/static assets
  • เพิ่ม offline fallback page และ network status banner
  • ไม่ queue order/payment/stock write

Risk: low

B. POS Offline Queue

แนะนำสำหรับคำว่า offline จริง แต่ต้องทำเป็น phase เพราะกระทบ data integrity.

  • เพิ่ม IndexedDB operation queue
  • กำหนด idempotency key ต่อ transaction
  • เพิ่ม sync state และ replay endpoint
  • เพิ่ม conflict policy สำหรับ order/payment/stock
  • ผูก feature gate offlinePos

Risk: medium/high

C. Enterprise Offline

ใหญ่สุด ครอบคลุมหลาย device, หลายสาขา และ inventory reconciliation.

  • device registration
  • multi-device conflict resolution
  • inventory reconciliation job
  • audit dashboard สำหรับ sync errors

Risk: high

Recommended Implementation Flow

1. App Shell manifest, service worker, offline fallback, installability.
2. Queue Contract IndexedDB schema, operation type, idempotency key, retry state.
3. Server Replay endpoint validates tenant/store/device/session and rejects duplicate operations.
4. POS Integration offline checkout queues operation, UI shows pending sync and lockouts.
5. QA Gate DevTools offline test, reconnect sync, duplicate-submit test, cross-tenant guard.

สิ่งที่ทำได้ทันทีหลังอนุมัติ

  • ถ้าเลือก A: ลงโค้ด PWA/offline shell ได้เลยแบบ TDD เท่าที่เหมาะกับ config/static behavior.
  • ถ้าเลือก B: เริ่มจาก spec + implementation plan แล้วทำ phase แรกของ queue contract ก่อน.
  • ถ้าเลือก C: ต้องแตกเป็น roadmap ย่อยก่อน เพราะใหญ่เกิน single implementation pass.
