แผนแก้: ปรับ Package ↔ Feature ให้ตรงความจริง

Store Management System (SaaS) — ปรับสิ่งที่ "โฆษณาบน landing" ให้ตรงกับ "สิทธิ์ที่ gate จริง" และ "ฟีเจอร์ที่มีจริง"

เวอร์ชัน v1 วันที่ 2026-06-29 แนวทาง: Build จริงทั้งหมด Workflow: Scope → Route → Implement → Review → Fix → Verify → Document

1. บริบท & ปัญหา (จากการวิเคราะห์)

ระบบมี 2 แหล่งความจริงที่ไม่ผูกกัน:

  • Gate จริง = PLAN_FEATURES ใน src/modules/billing/types.ts (บังคับจริงผ่าน canUseFeature/requireFeature)
  • ข้อความขาย = plan_settings.feature_lines ใน DB (แก้เองที่ /system/pricing) แสดงบน /pricing

ผลคือเกิดความไม่ตรงกัน 4 จุด ที่แผนนี้จะแก้:

#ปัญหาสถานะปัจจุบันการตัดสินใจ
1apiIntegration — Enterprise โฆษณา "เชื่อมต่อ API"ไม่มีฟีเจอร์จริง + ไม่มี gateBuild API จริง
2advancedReports / advancedPermissionsflag ตาย — ตั้งใน matrix แต่ไม่มีโค้ดเช็กImplement gating จริง
3คูปอง + สะสมแต้มล็อก Enterprise-only (Premium ก็ไม่ได้)ปลดลงมาที่ Premium
4Migration เปราะ — seed copy ของ Premium มี "จอแสดงผลลูกค้า" ที่ premium ไม่มีจริงรอด live เพราะ admin แก้มือ แต่ DB ใหม่จะโฆษณาเกินจริงเพิ่ม guard test + แก้ seed

3. แผนงานแยกเป็น 5 Workstreams

เรียงตามลำดับแนะนำ (A เริ่มได้ทันที, D ก้อนใหญ่สุด)

WS-A · ปลดคูปอง + สะสมแต้ม ลงมาที่ Premium เล็ก · ความเสี่ยงต่ำ

เปิด 2 flag ให้ premium — gate ที่ POS/member เปิดให้อัตโนมัติเพราะใช้ canUseFeature อยู่แล้ว ไม่ต้องแก้ logic เพิ่ม

  1. แก้ PLAN_FEATURES.premium: couponManagement: true, loyaltyPoints: true
  2. อัปเดต expectation ใน test (premium coupon/loyalty = true)
  3. อัปเดต feature_lines ของ premium: เพิ่มบรรทัด "คูปอง + สะสมแต้ม"
  4. ปรับ copy enterprise: เดิม "สมาชิก QR + สะสมแต้ม + คูปอง + จอลูกค้า" → ให้ enterprise ชูเฉพาะส่วนต่าง (จอลูกค้า, รายงานหลายสาขา, API) เพราะ coupon/loyalty ลงไป premium แล้ว
  5. เขียน migration อัปเดต plan_settings (conditional update กัน copy ที่ admin แก้เอง)

WS-B · advancedReports — ทำ gate จริง กลาง

นิยาม "รายงานขั้นสูง": แยก report ออกเป็น Basic (ทุก plan ที่มี reports.view) vs Advanced (standard+)

Basic (ทุก plan)Advanced (standard+ ผ่าน gate ใหม่)
ยอดขายรวม, ยอดขายรายวัน Top products, สัดส่วนช่องทางชำระเงิน, AOV, แยก QR/POS, Export CSV
  1. ใน reports/page.tsx คำนวณ advancedReportsEnabled = canUseFeature(state, "advancedReports")
  2. ส่ง prop ลง ReportsManager เพื่อแสดง/ซ่อนการ์ด Advanced + ปุ่ม Export (พร้อมข้อความ upsell เมื่อ lock)
  3. ใส่ requireFeature("advancedReports") ใน server action/route ของ Export
  4. เพิ่ม test: standard เห็น advanced, starter ไม่เห็น

ไฟล์: src/app/(dashboard)/reports/page.tsx · src/app/(dashboard)/reports/ReportsManager.tsx · (เพิ่ม) export action · tests/unit/*reports*

WS-C · advancedPermissions — ทำ gate จริง กลาง

นิยาม "สิทธิ์ขั้นสูง": = ความสามารถตั้ง per-user permission overrides (membership_permission_overrides) ผ่านหน้า Team Settings. Plan ต่ำ = ใช้สิทธิ์ตาม role default เท่านั้น; premium+ = ปรับสิทธิ์รายคนได้

  1. Gate ฝั่ง write เท่านั้น (ปลอดภัยกว่า): setPermissionOverrideAction ใน settings/team/actions.ts เรียก requireFeature("advancedPermissions")
  2. UI TeamSettings.tsx: ซ่อน/disable ตัวปรับ override + แสดงข้อความ upsell เมื่อไม่มีสิทธิ์
  3. เพิ่ม test: premium ตั้ง override ได้, standard ถูกปฏิเสธ
⚠️ จุดต้องตัดสินใจ (C-1): เมื่อ tenant ลดแพ็กเกจ ลงต่ำกว่า premium — override ที่ตั้งไว้เดิมควรทำงานต่อไหม?
ข้อเสนอ (default ปลอดภัย): ไม่แตะ permission-resolver.ts — override เดิมยัง apply (grandfather) แต่ สร้าง/แก้ใหม่ไม่ได้. เหตุผล: ถ้า ignore override ที่เป็นการ "ถอนสิทธิ์" จะทำให้ user ได้สิทธิ์คืนแบบไม่ตั้งใจ = ช่องโหว่ความปลอดภัย. การ gate แค่ write-path เลี่ยงปัญหานี้.

ไฟล์: src/app/(dashboard)/settings/team/actions.ts · src/app/(dashboard)/settings/team/TeamSettings.tsx

WS-D · API Integration — build จริง (Enterprise) ใหญ่ · ก้อนหลัก

สร้าง Public REST API พร้อมระบบ API key ต่อ organization, gate ด้วย apiIntegration

D-1 · Data layer

  • migration ตาราง api_keys: id, organization_id, name, key_prefix, key_hash (sha-256), scopes[], last_used_at, created_at, revoked_at
  • RLS: อ่าน/จัดการได้เฉพาะสมาชิก org (เขียนต้อง admin+); การ verify ฝั่ง API ใช้ service client

D-2 · Auth middleware สำหรับ API

  • helper authenticateApiKey(req): อ่าน Authorization: Bearer <key> → hash → lookup → ได้ organizationId
  • เช็ก canUseFeature(billingState, "apiIntegration") + เช็ก subscription ยัง active → 402/403 ถ้าไม่ผ่าน
  • อัปเดต last_used_at; รองรับ scope ต่อ endpoint

D-3 · Endpoints v1 (read-only ก่อน)

GET /api/v1/productsGET /api/v1/ordersGET /api/v1/inventoryGET /api/v1/customers

รูปแบบ: pagination + filter วันที่, ตอบ JSON มาตรฐาน, error envelope สม่ำเสมอ. (Write endpoints เป็น phase ถัดไป)

D-4 · หน้าจัดการ key + เอกสาร

  • หน้า /settings/integrations (หรือ /settings/api): สร้าง/ตั้งชื่อ/เพิกถอน key — โชว์ค่า key เต็มครั้งเดียวตอนสร้าง; ทุก action เรียก requireFeature("apiIntegration")
  • เพิ่ม tab ใน settings/layout.tsx ผูก featureKey: "apiIntegration" (ซ่อนอัตโนมัติเมื่อ plan ไม่มี)
  • เอกสาร API (markdown) + ตัวอย่าง curl
⚠️ จุดต้องตัดสินใจ (D-1): Scope รอบแรก — read-only 4 endpoint (แนะนำ, คุม risk) หรือรวม write ตั้งแต่แรก?
(D-2): Rate limiting — ใส่เลย(เช่น token bucket ต่อ key) หรือเลื่อนเป็น follow-up? แนะนำใส่ขั้นต่ำเพื่อกัน abuse.

WS-E · Guard test + migration hygiene เล็ก · สำคัญ (กันหลุดซ้ำ)

  1. Keyword-guard test: สร้าง map keyword→featureKey (เช่น "จอลูกค้า"→customerDisplay, "API"→apiIntegration, "คูปอง"→couponManagement). assert ว่า seed feature_lines ของแต่ละ tier ห้ามมี keyword ของ feature ที่ tier นั้นไม่มีใน PLAN_FEATURES → กันโฆษณาเกินจริงในอนาคต
  2. แก้ seed เปราะ: เขียน migration ที่ทำให้ historical seed copy ของ premium ไม่มี "จอแสดงผลลูกค้า" (customerDisplay เป็น enterprise-only); ตรวจ migration chain ทั้งหมดให้ลำดับสุดท้ายถูกต้องบน DB ใหม่

ไฟล์: tests/unit/plan-copy-feature-sync.test.ts (ใหม่) · migration แก้ seed

5. ความเสี่ยง & ข้อควรระวัง

ความเสี่ยงการรับมือ
WS-A เปิด coupon/loyalty ให้ premium แล้วกระทบคิดเงิน/แต้มที่ POSมี gate canUseFeature อยู่แล้ว — เพิ่ม test ครอบ premium; ทดสอบ preview รอบสั่ง-ชำระจริง
WS-C gate ผิดทางทำให้ override ความปลอดภัยรั่วgate เฉพาะ write-path ไม่แตะ resolver (ดู C-1)
WS-D key hash / leakเก็บเฉพาะ hash (sha-256), โชว์ key เต็มครั้งเดียว, รองรับ revoke, gate ทุก write ด้วย requireFeature
Migration conditional ไม่ match copy ที่ admin แก้ใช้รูปแบบ conditional เดิม (update เฉพาะ row ที่ตรง seed/ว่าง) + guard test กันหลุด

D-1 — API รอบแรก read-only 4 endpoint พอไหม หรือต้องการ write ด้วย?
D-2 — ใส่ rate limiting ตั้งแต่รอบแรกไหม?
นิยาม advancedReports — การแบ่ง Basic/Advanced ตามตารางใน WS-B โอเคไหม หรืออยากแบ่งเส้นอื่น?
